## P1 — nested-barrier handling reaches through a private transaction layout

`call_resolver.py` decides whether to re-raise with:

```text
getattr(_txn, "_state", None) ... getattr(_txn._state, "_txn_depth", 0)
```

That breaks the resolver context's documented transaction interface, which
currently promises only `commit()` / `rollback()`. Worse, absence or drift of
those private fields defaults to “outermost” and silently converts the barrier
instead of failing closed. The resolver should not infer nesting by reaching
through `CheckerStateTxn` internals.

Expose one structured transaction operation/property that owns this decision
(for example, rollback-and-report-whether-an-outer-transaction-remains), update
the resolver-context contract, and make an unsupported transaction fail closed
by propagating the barrier. The exact API is K's choice; keep depth ownership in
the transaction layer.

The current nested test does not cover this production branch. It manually
calls `owner.begin_resolution`, manually catches the exception, and manually
rolls back the inner/outer transactions. It would still pass if the resolver
catch converted the inner barrier, incremented the wrong counter, or installed
the wrong state. Add a test that exercises the actual catch/propagation path
and proves:

- inner probe rollback plus re-raise;
- outermost rollback plus silent Unknown deferral;
- exactly the intended nested/outer counters;
- no diagnostic, hard-error marker, or `rollbacks_exception` increment;
- exact state identity after both rollbacks.

Factoring the small handler into a testable authority is acceptable if that is
cleaner than manufacturing a natural nested source shape.
