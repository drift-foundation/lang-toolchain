The forcing shape is sound and materially advances the finding. It proves one
audited `NEEDS_EXPECTED` rollback after pending-lambda resolution and identifies
real survivors outside the advertised transaction boundary:
`pending_lambda_by_binding`, `binding_types`, `binding_for_var`, and the stored

the unowned ones. The fact that this source later emits the right single

Two research gaps remain before selecting an implementation.

## 1. Audit the checker-global publication explicitly

The probe does not currently snapshot `TypeChecker._lambda_fn_specs`. Static
inspection indicates the captureless pending lambda can publish a
`LambdaFnSpec` while it is typed inside the probe. A retry may overwrite an
equivalent key later, hiding the rollback leak in the final state. Extend the
work-only auditor to snapshot/diff at least `_lambda_fn_specs` at transaction
begin and immediately after rollback. Also report whether a leaked spec retains
the transaction-aware `call_info_by_callsite_id` object. Do not infer "only on
the retry" from the absence of a current auditor channel.

The work probe may remain characterization-only, but preserve exact output in
the addendum. The eventual in-tree red regression should assert full state
identity and therefore fail on the current tree.

## 2. Compare a mutation-site barrier against a syntax prewalk

K's Option A is plausible, but a pre-admission walk for pending binding ids is
not yet shown total. HVars may arrive without `binding_id`; the resolver's
current `binding_id_by_name` view is function-wide and is not a lexical-
shadowing authority. An admission walk also needs continuing awareness of
aliases and every future deferred producer.

Please evaluate a stronger Option A variant: make the operation that consumes
pending semantic state itself the transaction barrier.

- Route HCall, HInvoke, and any parent-finding value-use totalization through
  one pending-lambda resolution/take authority.
- Its first action, before stamping the external HLambda, typing arguments,
  popping the pending entry, or writing binding metadata, checks whether a
  checker probe transaction is active.
- If active, signal a structured internal `NEEDS_EXPECTED` barrier. The probe
  rolls back without emitting diagnostics or installing the hard-error marker.
- With nested transactions, inner scopes must roll back and propagate the
  signal; only the outermost active probe converts it into the ordinary silent
  expected-type deferral. Returning Unknown from an inner probe and continuing
  the outer probe could incorrectly turn the barrier into a committed hard
  error.
- Outside a probe, the same authority performs the one real pending-lambda
  resolution. Exact binding identity comes from the live resolution path, so
  the design does not need a speculative name lookup.

One possible representation is an explicit pending-lambda owner whose mutation
methods refuse to run while `FnCheckState` has an active transaction. That
would make future direct map pops harder to add accidentally. This is a design
candidate, not a prescribed class/API.

Compare this mutation-site form with the prewalk on:

- completeness under unlinked and shadowed HVars;
- HCall/HInvoke parity and the parent's planned HVar value-use path;
- nested transaction behavior;
- whether the expected-type retry preserves the original B5 COMPLETE cases;
- how a future deferred producer is forced through the same authority;
- probe/corpus counter semantics and performance.

Add positive work probes for an otherwise-complete nested call through a
pending lambda, including a nested-transaction shape if constructible. A
barrier that merely restores safety by disabling a previously valid B5
resolution is not sufficient; the enclosing expected-context retry must still
produce the same function type, CallInfo/coercions, diagnostics, and runtime
result.

If the mutation-site barrier has a counterexample, retain the prewalk or choose
another design and record the evidence. If it holds, it appears more robust
than predicting semantic mutation from syntax and should become the leading
Option A form. Option D remains the escalation path if another unrelated
speculative-state escape family is found.

Continue with work-folder probes only while the full suite is active. No shared
compiler/test/spec/history edit is authorized by this review.
