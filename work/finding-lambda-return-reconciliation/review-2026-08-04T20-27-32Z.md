# Reviewer handoff: begin inferred-lambda return reconciliation

Timestamp: 2026-08-04T20:27:32Z

The next serial finding is ready for implementation.

## Why this finding is next

This is the remaining P1 in the queue.  The primary `TypeChecker` can infer an
unannotated lambda from one exit while silently ignoring incompatible earlier
or later explicit returns.  The 0.35.0 hidden-function re-check catches the
minimal source repro later, but that is a downstream safety net and does not
repair the first-pass authority that creates the lambda function type and
CallInfo.

## Refreshed evidence

The current 0.35.0 tree still contains `_find_return_expr` and still discards
the effective type returned by `_type_return_value` at `HReturn` sites.  I reran
the two direct boundary probes after the 0.35.0 commit:

```text
2 failed in 0.51s
```

Both calls are inferred as `Int`; both fail only because the expected primary
`String`/`Int` mismatch diagnostic is absent.  This is the intended red state.

`doc/refactor_triggers.md` was rescanned and no trigger matches.  No spec change
is proposed: section 22.1.1 already requires body-based lambda return inference.

## Requested implementation

Use `FINDING.md` and the refreshed `PLAN.md` as the research package.  The core
constraints are:

1. Move the direct first-pass probes into a new in-tree test and establish red
   before changing the compiler.
2. Capture every `HReturn`'s effective type during its single existing
   `_type_return_value` visit, in a collector isolated by nested-lambda
   boundaries.
3. Delete `_find_return_expr`; choose the existing deterministic candidate
   (value tail, else first valued return, else `Void`) from one-pass results.
4. Reconcile all observations only for genuinely inferred lambdas, suppressing
   `Unknown` cascades and accepting normalized nominal equality.
5. Do not re-type return expressions, invent a late coercion/LUB, copy coercion
   side tables, or add a call-resolver inference route.
6. Pin primary-boundary placement, arm-local scope safety, bare/value conflicts,
   nested-lambda isolation, clean driver dedup, and compile/run positives.

The plan is deliberately explicit but not infallible.  If source evidence
invalidates a proposed mechanism or reveals a language-contract choice, record
the evidence in `PROGRESS.md` and stop for review/approval rather than forcing
the plan.
