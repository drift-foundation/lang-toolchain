# Option B Transition Plan: Packages as Distribution Containers

## Status: proposed plan (review before sequencing)
## Date: 2026-04-02

---

## Target architecture

After this plan completes:
- Packages are distribution/provenance containers (versioning, signing, trust)
- Package payloads contain **declared HIR** — the typed, name-resolved,
  export-annotated intermediate produced by parsing + declaration
- Consumers compile package HIR through the **same canonical pipeline**
  as source inputs: type checking → generic instantiation → MIR lowering
  → string_arc → codegen
- There is **one semantic mode** after ingress. No code path checks
  "is this from a package?"
- No MIR serialization. No TypeId remapping. No signature dual-path
  resolution. No `__wrap_method` wrappers. No `_build_package_consumer_unit`

---

## Why HIR is the right serialization layer

### Why MIR is too late

MIR is the output of HIR-to-MIR lowering. Lowering makes irrevocable
decisions that depend on the **consumer's** context:
- `has_drop(T)` → determines scope-exit drops (depends on destructor_fns)
- `_param_is_string(T)` in string_arc → determines retain/release insertion
  (depends on TypeId identity)
- `_should_copy_value(T)` → determines move-vs-copy (depends on copy_status)
- Call target resolution → determines direct-vs-indirect-vs-wrapper routing
  (depends on CallInfo)
- FnResult wrapping → determines ABI shape (depends on can-throw status)

All of these are **consumer-side facts** that the producer cannot know.
Serializing MIR freezes the producer's answers and forces the consumer
to accept them — or compensate with wrappers, remapping, and post-hoc
fixes. This is the source of every boundary bug we've had.

### Why AST is too early

AST is pre-name-resolution, pre-type-declaration. Serializing AST means
the consumer must re-parse module structure, re-resolve imports, re-declare
types. This is ~2s of work that's genuinely redundant — the producer
already did it, and the results are deterministic.

### Why declared HIR is right

The output of `parse_drift_workspace_to_hir` is:
1. **Type table** with all nominals declared, all type aliases resolved,
   all struct/variant/interface schemas populated with TypeExpr fields
2. **Signatures** with TypeExpr-based param/return types (name-based,
   re-resolvable in any consumer context)
3. **HIR blocks** — function bodies in sugar-free HIR form, with variable
   bindings, control flow, and expression nodes intact
4. **Export interfaces** — pub/private visibility, re-exports
5. **Exception schemas** — structured error definitions
6. **Trait metadata** — trait definitions, impl headers, require clauses

This is the **last representation that is context-independent**. Everything
after this point (type checking, generic instantiation, MIR lowering)
depends on the full compilation context, which only the consumer has.

### What declared HIR already covers

Generic templates are already serialized as HIR in the current package
format (`encode_generic_templates` in `provisional_dmir_v0.py`). This
plan extends the same approach to ALL functions, not just generics.
The serialization infrastructure exists — `_to_jsonable()` / `from_jsonable()`
handles all HIR node types via dataclass registry.

### What must be serialized alongside HIR

HIR alone is not self-contained. The consumer needs these to compile it:

| Data | Currently serialized? | Needed for Option B? |
|------|:--------------------:|:--------------------:|
| **HIR function bodies** (HBlock trees) | Only for generic templates | Yes, for all functions |
| **Signatures with TypeExpr** (param types, return type) | Yes (v1 concrete sigs) | Yes |
| **Type declarations** (struct/variant/interface schemas) | Yes (type_table section) | Yes |
| **Type aliases** | Yes | Yes |
| **Exception schemas** | Yes | Yes |
| **Trait definitions + impl headers** | Yes (trait_metadata, impl_headers) | Yes |
| **Require clauses** (trait bounds on functions) | Yes (generic templates) | Yes, for all functions |
| **Export/visibility metadata** | Yes | Yes |
| **Constants** (including internal, for generic re-instantiation) | Yes | Yes |
| **NodeId / BindingId assignments** | No | No (regenerated by consumer checker) |
| **Per-expression type map (expr_types)** | No | No (produced by consumer checker) |
| **CallInfo (resolved call targets)** | No | No (produced by consumer checker) |
| **MIR** | Yes (current format) | **No** |
| **Raw TypeIds** | Yes (v0/v1 format) | **No** |
| **Canonical keys** | Yes (v1 format) | **No** |

Everything the consumer needs is already serialized in the current
format — except HIR for non-generic functions. The plan adds that one
field and removes MIR, raw TypeIds, and canonical keys.

### Compilation time impact

Current full compile (stdlib + consumer): ~12s total
- Parsing + declaration: ~2s (what package consumption saves today)
- Type checking: ~1s
- MIR lowering + string_arc: ~2s
- Codegen: ~7s

With HIR packages, the consumer skips parsing + declaration (~2s) but
runs type checking + MIR lowering + string_arc + codegen on package
functions. Net impact vs current MIR packages: **~1s additional** (the
type-checking pass that MIR packages currently skip). This is the only
real cost of Option B.

For stdlib (~30 files, ~6000 lines), type checking is ~0.5s. The
consumer already runs string_arc and codegen on ALL MIR. The marginal
cost is small.

## Phase plan

### Phase 0: Serialize nothrow status and skip FnResult wrapping [IMMEDIATE]

**Goal**: Fix the bookkeeper leak. This is the smallest change that
proves we are moving toward B.

**What changes**:
- Package producer: ensure `declared_can_throw` is serialized on every
  signature in the package payload (already present for most signatures
  in the current format — verify completeness)
- Consumer: in wrapper synthesis (`driftc.py:2416`), read
  `declared_can_throw` from the target's package signature. If the
  target is provably nothrow (`declared_can_throw == false`), **do not
  generate a FnResult wrapper**. Call the target directly with the
  consumer's return type.

**Why this is an Option B step**: This eliminates the FnResult ABI
wrapper for nothrow cross-package calls. Under Option B, there are no
wrappers at all — this is the first deletion.

**Files**:
- `driftc.py` — wrapper synthesis loop (~line 2392-2421)
- `provisional_dmir_v0.py` — verify declared_can_throw serialization

**Dead code after this phase**:
- FnResult wrapper generation for nothrow targets
- The `boundary_ret_type_id` machinery for nothrow methods (partial — still needed for can-throw methods until Phase 3)

**Regressions**:
- `test_pkg_map_literal_string_leak.py::test_map_literal_format_int_logger_emit` — currently fails, should pass after fix
- New test: nothrow cross-package method call returns bare value (no FnResult wrapper)
- Existing pkg_consumer_runner suite must remain green

**Prerequisites**: None. This is the entry point.

### Phase 1: HIR serialization for all package functions [CORE]

**Goal**: Package payloads contain declared HIR for all functions, not
just generic templates. The producer serializes HIR; the consumer can
load it.

**What changes**:
- Package producer: extend `encode_generic_templates` (or factor out
  a new `encode_function_hirs`) to serialize HIR for ALL exported
  functions, not just generics
- New payload field: `hir_funcs` alongside existing `mir_funcs` and
  `generic_templates`
- HIR includes: normalized function bodies, binding info, source spans
  (optional)
- Signatures already have TypeExpr fields — no change needed there

**What does NOT change yet**:
- MIR is still serialized (both paths coexist temporarily)
- Consumer still uses MIR path by default
- No consumer-side changes

**Why this phase exists**: Proves that HIR serialization produces a
complete, deserializable payload before we depend on it.

**Files**:
- `provisional_dmir_v0.py` — new encode/decode functions for HIR
- `driftc.py` — package emission (~line 10580) adds `hir_funcs`
- `parser/__init__.py` — may need minor exports for HIR serialization

**Dead code**: None yet (additive phase).

**Regressions**:
- Round-trip test: serialize HIR → deserialize → compare AST structure
- For each stdlib function, HIR round-trip produces structurally identical HIR

**Prerequisites**: Phase 0 (establishes that we are reducing wrapper dependence)

### Phase 2: Consumer compiles from package HIR [PIVOT]

**Goal**: When the consumer loads a package, it deserializes HIR and
feeds it through the standard compilation pipeline (type checking →
MIR lowering → string_arc → codegen). No MIR loading, no TypeId
remapping, no signature dual-path.

**What changes**:
- Consumer: new ingestion path that:
  1. Loads package type table schemas (struct/variant/interface
     declarations, type aliases) → declares them into the consumer's
     TypeTable
  2. Loads package HIR functions → adds them to the consumer's
     `func_hirs_by_id`
  3. Loads package signatures (TypeExpr-based) → resolves them in the
     consumer's TypeTable context
  4. Package functions then flow through the SAME `compile_stubbed_funcs`
     pipeline as source functions
- The consumer's type checker runs on package HIR in the consumer's
  context → produces expr_types, call_info, etc.
- HIR-to-MIR runs in the consumer's context → produces MIR with the
  consumer's TypeIds natively (no remapping)
- string_arc runs on the consumer-produced MIR → correct fn_infos,
  correct param type recognition

**What this eliminates**:
- `_build_package_consumer_unit` (~700 lines)
- `_remap_mir_func_typeids` and `_validate_remap_completeness`
- Signature dual-path resolution (TypeExpr vs raw TypeId + tid_map)
- BFS reachability for package MIR (consumer's reachability analysis
  works on MIR it produced itself)
- `__wrap_method` synthesis entirely (consumer compiles package functions
  directly — no boundary exists after ingestion)
- Return TypeId reconciliation between checker and package paths
- `boundary_ret_type_id` machinery (no wrappers → no boundary ABI)

**What this preserves**:
- Type table schema linking (declarations, not TypeIds — using TypeExpr/
  canonical keys for struct/variant/interface identity)
- Package signing, trust, version resolution
- Export/visibility enforcement (pub annotations on package HIR)

**Files**:
- `driftc.py` — new ingestion function replacing
  `_build_package_consumer_unit` (~200 lines replacing ~700)
- `type_table_link_v0.py` — simplify to declaration linking only
  (remove TypeId remapping, remove canonical key computation for every
  TypeId)
- `provisional_dmir_v0.py` — add HIR decode path
- `driftc.py` — `compile_stubbed_funcs` may need minor adaptation to
  accept mixed source+package HIR inputs

**Dead code after this phase** (deletable):
- `_build_package_consumer_unit` (entire function)
- `_remap_mir_func_typeids`, `_validate_remap_completeness`
- Signature raw TypeId + tid_map fallback path
- `__wrap_method` synthesis loop
- `boundary_ret_type_id` on FnSignature
- `_is_cross_package_boundary` / `_method_boundary_visible` checks in
  type_checker.py
- `call_resolver.py` wrapper upgrade decision
- `llvm_codegen.py` `_resolve_call_target_symbol` boundary routing
- `pkg_fn_infos` construction from serialized signatures
- `pkg_tid_universes`, `pkg_typeid_maps`
- TYPEXPR debug assertions (no dual path to assert against)

**Regressions**:
- All existing e2e tests pass through the new path
- `pkg_consumer_runner.py` full suite passes
- The bookkeeper leak reproducer passes
- New mode-equivalence test: compile same program via source and via
  HIR-package, diff the LLVM IR — must be identical (modulo symbol
  ordering)

**Prerequisites**: Phase 1 (HIR serialization exists and is validated)

### Phase 3: Remove MIR serialization from package format [CLEANUP]

**Goal**: Package payloads no longer contain serialized MIR. The
`mir_funcs` field is removed from the payload schema. Payload version
bumped.

**What changes**:
- Package producer: remove `encode_mir_funcs` from package emission
- Package consumer: remove `decode_mir_funcs`
- Payload version: bump to 2 (consumer rejects v0/v1 payloads)
- Since we assume no backward compat, this is a clean break

**Dead code after this phase** (deletable):
- `encode_mir_funcs`, `decode_mir_funcs` in `provisional_dmir_v0.py`
- MIR serialization utilities (TypeId encoding in MIR instructions)
- Remaining TypeId remapping infrastructure in type_table_link_v0.py
  (canonical key computation per-TypeId, tid_map construction)

**Files**:
- `provisional_dmir_v0.py` — remove MIR encode/decode
- `type_table_link_v0.py` — simplify to declaration-only linking
- `driftc.py` — remove MIR loading branches

**Regressions**:
- All existing tests pass with payload_version=2
- Rebuild stdlib package, rebuild all downstream packages
- pkg_consumer_runner passes with new packages

**Prerequisites**: Phase 2 (consumer no longer reads MIR from packages)

### Phase 4: Simplify type table linking [STRUCTURAL]

**Goal**: Type table linking becomes declaration merging, not TypeId
remapping. The consumer's TypeTable gets package type declarations
(struct schemas, variant schemas, interface schemas, type aliases)
merged by identity (package_id + module_id + name), then resolves all
TypeIds itself through normal compilation.

**What changes**:
- `type_table_link_v0.py`: replace the current two-phase canonical-key
  TypeId remapping with a simpler declaration merge:
  1. For each package type declaration, check if the consumer already
     has it (by module_id + name)
  2. If not, declare it in the consumer's TypeTable
  3. No TypeId mapping needed — the consumer's type resolution creates
     TypeIds naturally during compilation
- Package payload: type_table section contains only declarations
  (schemas + aliases), not runtime TypeIds or canonical keys

**Dead code after this phase** (deletable):
- Canonical key computation (`_canonical_key_for_tid`, `_compute_canonical_keys`)
- TypeId mapping tables (`pkg_typeid_maps`)
- `import_type_tables_and_build_typeid_maps` (replace with `merge_type_declarations`)
- Validation infrastructure for TypeId remapping
- Phase A/B canonical key system in type_table_link_v0.py (~1000 lines)

**Files**:
- `type_table_link_v0.py` — rewrite to ~200 lines (declaration merge only)
- `driftc.py` — simplify package loading sequence

**Regressions**:
- Cross-package type identity: struct from package A used in package B
  consumer resolves to same TypeId
- Generic instantiation: `HashMap<String, V>` from stdlib, instantiated
  with consumer's V=String, produces correct TypeId

**Prerequisites**: Phase 3 (no MIR serialization means no TypeId
remapping consumers)

### Phase 5: Delete remaining mode-sensitive code [FINAL]

**Goal**: No code in the compiler checks "is this from a package?"
for semantic decisions. Package origin is metadata only.

**What to audit and remove**:
- `explicitly_packaged_modules` — no longer meaningful
- `source_modules` — already eliminated by wrapper convergence, verify
  no remaining references
- Package-specific BFS reachability — standard reachability works on
  consumer-compiled MIR
- Package-specific K39 scanning — standard K39 works on consumer context
- `is_exported_entrypoint` as a semantic flag — becomes metadata only
  (controls what the package exports, not how it's compiled)

**Files**: grep for `package`, `pkg_`, `external_`, `boundary_` in
driftc.py, type_checker.py, call_resolver.py, llvm_codegen.py

**Dead code**: everything flagged by the audit

**Regressions**:
- Full downstream validation (drift-web, net.tls, mariadb-client)
- pkg_consumer_runner suite
- Source-vs-package IR equivalence test from Phase 2

**Prerequisites**: Phase 4

## Target representation detail

### What a v2 .dmp payload contains

```
{
  "payload_kind": "drift-hir",
  "payload_version": 2,
  "type_declarations": {
    // Struct schemas (name, fields as GenericTypeExpr, type params)
    // Variant schemas (name, arms, type params)
    // Interface schemas (name, methods, type params, parents)
    // Type aliases (name, target TypeExpr)
    // Exception schemas (name, fields)
  },
  "signatures": {
    // Per-function: name, param TypeExprs, return TypeExpr,
    // declared_can_throw, is_pub, is_method, type_params,
    // impl_type_params, is_extern_c
    // NO raw TypeIds (TypeExpr only)
  },
  "hir_funcs": {
    // Per-function: normalized HIR body (same format as generic
    // templates today)
    // Includes: binding_names, binding_types as TypeExpr,
    // control flow, expressions
  },
  "trait_metadata": { ... },
  "impl_headers": { ... },
  "consts": { ... },
  "exports": { ... },
  "reexports": { ... }
}
```

No TypeIds in the payload. No MIR. No canonical keys. All type
references are TypeExpr (name-based, re-resolvable).

### What the consumer does with this

1. Load type declarations → merge into consumer TypeTable
2. Load signatures → resolve TypeExprs in consumer context → FnSignatures with consumer TypeIds
3. Load HIR funcs → add to consumer's `func_hirs_by_id`
4. Run `compile_stubbed_funcs` on ALL functions (source + package) through the single pipeline:
   - Type checking (produces expr_types, call_info)
   - Generic instantiation (K39 runs in consumer context)
   - HIR-to-MIR lowering (uses consumer's has_drop, consumer's TypeIds)
   - string_arc (uses consumer's fn_infos — correct, complete, one source)
   - Post-pass validation
5. Emit IR from unified MIR

## The first real architectural slice

**Phase 0 is the entry point.** It is small (< 50 lines changed), directly
fixes the bookkeeper leak, and proves the direction by eliminating
the first category of unnecessary FnResult wrapping.

But Phase 0 is a targeted fix. **Phase 1 is the first true architectural
slice** — it extends HIR serialization from generics to all functions.
This is the irreversible step: once package payloads contain HIR,
Phase 2 can consume them through the standard pipeline.

The smallest change that meaningfully reduces semantic dependence on
package MIR is Phase 0 + Phase 1 together. Phase 0 removes the wrapper
for nothrow calls. Phase 1 creates the alternative payload that makes
MIR optional. Neither is large individually.
