## P1 — constructor-context fallback runs before ordinary symbol resolution

`call_resolver.py:6840-6858` turns any unqualified call whose spelling
matches a visible/current/core variant arm into `E-CTOR-EXPECTED-TYPE` when
the expected type is non-variant. This happens before both struct-constructor
resolution (`:6859`) and free-function resolution (later near `:6914+`).

Variant-arm spelling is not proof that a particular `HCall` denotes that
variant constructor. The new fallback therefore globally reserves common
names such as `Ok`, `Err`, `Some`, and `None` ahead of actual value symbols.

Two certified-positive regressions were independently reproduced:

```drift
import std.core as core;

fn Some(x: Int) nothrow -> Int { return x; }
pub fn main() nothrow -> Int { return Some(0); }
```

Certified current toolchain: exit 0. Revision 9: one
`E-CTOR-EXPECTED-TYPE` at the `Some(0)` call.

```drift
import std.core as core;

pub struct Some { pub value: Int }
pub fn main() nothrow -> Int {
	val x: Some = Some(value = 0);
	return x.value;
}
```

Certified current toolchain: exit 0. Revision 9: two
`E-CTOR-EXPECTED-TYPE` diagnostics, including one at the struct call.

Repros are preserved in the nested finding as:

- `repro_free_function_some_collision.drift`
- `repro_struct_some_collision.drift`
- `repro_free_function_ok_collision.drift` (the old AST rewrite already
  hijacked this spelling; deleting that seam should finally allow the normal
  function symbol rather than replacing one hijack with another)

Fix the precedence, not the spelling list. A no-context variant diagnostic
may be emitted only after an actual binding/function/struct candidate has not
owned the call. Do not infer "this is a constructor" merely from an arm name
present somewhere in the type table. Preserve these cases:

- an expected public variant + matching arm resolves as its constructor;
- no expected variant and no ordinary callable/struct candidate gets the
  clean `E-CTOR-EXPECTED-TYPE` diagnostic;
- an ordinary function or struct named `Ok`/`Some` resolves normally when
  its own signature and expected type match;
- if an ordinary candidate exists but its arguments do not match, its normal
  overload/constructor diagnostic should not be replaced by the unrelated
  expected-variant message.

Regression-first: add compile/run positives for at least the direct free
function and annotated struct cases before changing the resolver. A new test
file avoids needing another approval to edit an unrelated existing test.
Keep the two new `Ok(...)` no-context negatives green.

## P1 — runtime ConstShare test does not read either promised owner

`test_phase5_public_result_ctor_payload_runs` claims that the source binding
is read after construction and the `Ok` payload is consumed. At
`test_const_share_phase5_implicit_duplication.py:450-460`, however,
`use_arc(a)` returns the constant `1` without dereferencing `a`, and the
`Ok(v)` arm returns the constant `2` without dereferencing `v`.

The structural half correctly proves that the wrapper was inserted. The
full-run companion is meant to prove that both resulting owners are valid
through lowering/runtime; merely passing/binding and dropping them does not
make the semantic result depend on either payload.

Strengthen the already-approved test so it calls `a.get()` after
`Ok(a)`, calls `v.get()` in the `Ok` arm, and derives the asserted exit code
from both strings' lengths/content. Add a timeout (and preferably captured
stderr) to the final binary execution. This keeps the structural and runtime
halves complementary rather than duplicating a compile-only acceptance
claim.
