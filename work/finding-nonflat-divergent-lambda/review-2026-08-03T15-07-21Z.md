### 1. P1 — an uninvoked **capturing** pending lambda still reaches lowering as raw `HLambda`

**Status: Confirmed statically.**

The new flush at `lang/driftc/type_checker.py:13688-13698` calls `type_expr(_pend_lam)` without an expected type. In that no-expectation `HLambda` route, `lang/driftc/type_checker.py:7934-7941` discovers captures and then returns `Unknown` immediately when captures exist. It emits no capture diagnostic and records no `fnptr_consts_by_node_id` entry.

The flush then stores `Unknown`, removes the pending entry, and `_apply_fnptr_consts()` has nothing with which to replace the original initializer. The raw `HLambda` therefore remains in the `HLet`, preserving the original `No MIR lowering for expr HLambda` failure for this shape.

This contradicts Revision 3's claim that the flush routes capturing lambdas to the standard capture rejection. The five new child tests cover only captureless lambdas.

A minimal boundary case is:

```drift
pub fn main() nothrow -> Int {
    val x = 1;
    val t = || => { x };
    return 0;
}
```

`t` is never invoked, so only the new flush resolves it. Bare stored capturing lambdas are deliberately unsupported in v1; this must produce the same single, spanned “capturing lambdas cannot be coerced to function pointers” diagnostic as the invoked form, with no `Unknown` cascade and no lowering traceback.

**Proposed closure:** centralize the capture rejection used by the expected-function and no-expectation `HLambda` branches, or explicitly diagnose it in the flush route before allowing the raw node onward. Add an end-to-end negative for an uninvoked implicit capture; an explicit-capture companion would protect the parallel branch.

### 2. P1 — the flush can emit a `LambdaFnSpec` whose ABI contains `Unknown`

**Status: Confirmed checker/codegen path; the exact source diagnostic policy is open for K to decide.**

With no expected function type, an unannotated lambda parameter defaults to `self._unknown` at `lang/driftc/type_checker.py:7405-7449`. The no-expectation captureless route then unconditionally constructs a function type and `LambdaFnSpec` from those parameter/return types at `lang/driftc/type_checker.py:7942-7961`.

The new flush makes that route live for an unconstrained, uninvoked lambda such as:

```drift
pub fn main() nothrow -> Int {
    val id = |x| => { x };
    return 0;
}
```

There is no callsite from which to infer `x`. The resulting spec has `Unknown` parameter and return types, while LLVM type mapping has no representation for `TypeKind.UNKNOWN` (`lang/codegen/llvm/llvm_codegen.py:8659-8750`) and raises `NotImplementedError` for unsupported parameter types. No typed-HIR validation in this route rejects the unresolved function signature first.

This is another checker/lowering boundary hole introduced into the child finding's claimed “ordinary no-expectation typing” closure. The compiler must not create an emit-ready `LambdaFnSpec` with unresolved ABI types.

**Proposed closure:** after no-expectation typing, require every lambda parameter and return type needed by the emitted function signature to be concrete. If source inference has no constraint, emit a clean source diagnostic identifying the parameter/return that needs an annotation. If Drift instead intends unused unconstrained lambdas to be legal, K should document and implement a non-emitting representation that never reaches MIR/LLVM; silently treating `Unknown` as an ABI type is not viable. Add a driver negative proving no traceback/internal contract diagnostic.

### 3. P1 — `try` catch arms are treated as reachable even when the attempt cannot throw

**Status: Confirmed analysis behavior; source consequences are inferred and should be probe-verified.**

Revision 3 correctly removes a caught body `THROWS` member, but all catch arms are still unioned unconditionally in `_stmt_exits()` at `lang/driftc/stage1/hir_flow.py:103-115`. The reachable-break authority similarly scans every catch at `lang/driftc/stage1/hir_flow.py:202-205`, and the throw-effect authority scans every catch arm at `lang/driftc/stage1/hir_flow.py:356-372` even when the attempt/body has no possible throw.

That makes unreachable handler code affect both terminal flow and `nothrow` checking. For example, in this loop the catch-side `break` cannot execute because `continue` cannot throw:

```drift
val f = || -> Int => {
    while true {
        try { continue; } catch { break; }
    }
};
```

`block_contains_reachable_break()` nevertheless sees the catch `break`, gives the loop `FALLTHROUGH`, and can reject this genuinely non-fallthrough lambda. The effect-side analogue is an effectless attempt with a throwing catch arm inside a `nothrow` lambda: the handler throw is currently counted even though the handler cannot be entered.

**Proposed closure:** gate catch-arm exits, breaks, and throw effects on whether the attempt can throw. Do not infer that solely from `Exit.THROWS`: the terminal-flow analysis deliberately does not add a `THROWS` exit for an ordinary can-throw call that can also return. Reuse or expose the shared effect decision with the relevant injected `CallInfo` predicate so the flow and effect authorities agree. Add unit cases for unreachable catch `break`/`return`/`throw`, plus compile/run positives for the divergent loop and `nothrow` shapes. If Drift intentionally treats handlers as reachable for an effect not represented in HIR, K should record that semantic evidence and narrow the module's “every CFG path” contract accordingly.

### 4. P1 — the new lambda-spec drain is not closed over typed-function state or generic instantiations

**Status: Confirmed structural omission; the predicted nested-generic failure needs a focused repro.**

The loop at `lang/driftc/driftc.py:7643-7815` now discovers `LambdaFnSpec`s registered while rechecking an earlier spec. That is the right scheduling direction, but the freshly produced `lambda_typed_fn` is neither:

- registered as `typed_fns_by_id[spec.fn_id]`, nor
- passed to `_queue_instantiations(spec.fn_id, lambda_typed_fn)`.

The last `_drain_instantiations()` call is before this worklist, at `lang/driftc/driftc.py:7534`, and there is no corresponding drain afterward.

Two dependent contracts therefore remain open for a spec that truly appears during this new loop:

1. A still-deeper nested spec uses its parent `spec.fn_id` as `origin_fn_id`, but `typed_fns_by_id.get(spec.origin_fn_id)` at `lang/driftc/driftc.py:7690-7695` returns nothing because the parent result was never registered. The comment promising transitive origin type-parameter forwarding is not satisfied.
2. Generic calls/constructors first recorded while rechecking that newly discovered spec never enter the instantiation queue, so their monomorphized targets may remain unemitted or unreconciled.

The hidden-lambda worklist explicitly performs both registration and `_queue_instantiations()` at `lang/driftc/driftc.py:7208-7222`; the captureless worklist needs an equivalent closure strategy. A single extra drain may itself generate more lambda specs, so K should verify whether these worklists require a joint fixed point rather than another one-way pass.

**Proposed regression shape:** force at least one unannotated pending lambda to be discovered only while rechecking another uninvoked spec, then put a generic call and a reference to the generic origin's type parameter in that deeper body. A compile/run driver should prove that the nested symbol and its generic instantiation are both emitted. K may disprove the predicted failure if another queue owns these records, but that ownership is not present in the reviewed loop and should be demonstrated before sign-off.
