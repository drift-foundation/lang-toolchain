# Revision 4 static review — 2026-08-03T15:33:01Z

## Verdict

**Changes requested.** Revision 4 closes the two direct pending-lambda boundary holes from the previous review: a pending capturing lambda now stops with a source diagnostic, and an unconstrained pending lambda cannot proceed to lowering with an `Unknown` function ABI. The new `CallInfo` predicates also connect both flow consumers to resolved call effects, and the captureless drain now registers typed parents and queues generic instantiations as requested.

Two P1 authority claims are still incomplete, however:

1. the throw-effect query used to decide whether catches are reachable is not itself CFG-reachability-aware, so dead throws still make dead catches live and dead branches still make a `nothrow` lambda appear throwing;
2. the compiler's new quiescence loop covers captureless lambda specs and generic instantiations, but not two other function producers that run before it: throw-adaptation thunks and stage-2 hidden lambdas.

The new nested-generic test also does not create a lambda spec during the drain as its name and comment claim, so it cannot protect the scheduling route added in this revision. I found two smaller issues in the borrowed-capture diagnostic classification and persistent status/test documentation.

This was a static review. I did not rerun K's reported 133/133 targeted battery, the full suite, or corpus gates. The diagnoses and repro shapes below should be independently probe-verified by the implementer; where I propose a patch structure, it is a recommendation rather than an instruction to preserve it if a smaller shared authority fits the current tree better.

`doc/refactor_triggers.md` has no registered trigger matching these HIR-flow or compiler-worklist shapes. The scheduler omission may nevertheless justify a small joint-worklist refactor because moving another one-way pass would not close producer cycles.

## Findings

### 1. P1 — the catch-reachability predicate still counts unreachable throws

**Status: Confirmed statically against the shared analysis; the exact source diagnostics should be probe-verified.**

Revision 4 gates `HTry` catch contributions with:

- `any(_can_throw(s, call_can_throw) for s in stmt.body.statements)` in `block_exits()` at `lang/driftc/stage1/hir_flow.py:120-123`;
- the same shape in `block_contains_reachable_break()` at `lang/driftc/stage1/hir_flow.py:218-219`;
- the same direct statement scan inside `_can_throw(HTry)` at `lang/driftc/stage1/hir_flow.py:388-394`.

That is a useful effect gate, but `_can_throw()` is a structural descendant walk, not a reachable-effect walk. `HBlock`, `HIf`, `HLoop`, and `HReturn` are all in `_RECURSIVE_TYPES` at `lang/driftc/stage1/hir_flow.py:272-326`; their children are traversed unconditionally at lines 397-398. Consequently:

- a `throw` after a terminating `return`, `continue`, or `break` is counted;
- the untaken arm of a literal `if true`/`if false` is counted, even though `block_exits()` deliberately folds that same literal condition;
- an `HTry` whose only syntactic throw is unreachable is classified as able to enter its catches.

This contradicts `lambda_body_can_throw()`'s documented contract, “True iff EXECUTING `lam`'s body can raise,” and makes the new catch gate disagree with the terminal-flow authority on statement reachability.

Two boundary shapes to probe are:

```drift
val f = || nothrow => {
    if false {
        throw ExcA(kind = 1);
    }
    0
};
```

The false branch cannot execute, but the current reflective `HIf` walk reaches `HThrow` and is expected to reject the `nothrow` lambda.

```drift
val f = || -> Int => {
    while true {
        try {
            continue;
            throw ExcA(kind = 1);
        } catch {
            break;
        }
    }
};
```

`block_exits()` correctly stops sequential flow at `continue`, but the independent `any(_can_throw(...))` scan still sees the later `throw`, marks the catch reachable, sees its `break`, and can incorrectly make the infinite loop fall through. If the source checker rejects a statement after `continue` before this analysis, the equivalent literal-false-arm form should exercise the same semantic error without relying on dead-statement acceptance.

**Proposed closure:** give the effect authority the same reachability rules as the exit authority. One plausible shape is a `_block_can_throw()` sequential walk that stops after a statement loses `FALLTHROUGH`, plus special `HIf` handling that follows only the selected literal arm and otherwise unions both arms. A more robust option is one shared per-statement summary carrying both exits and `can_throw`, which prevents the two answers drifting again. Either is acceptable if K can demonstrate that it is total over the HIR variants and preserves conservative behavior for unknown variants/missing `CallInfo`.

Pins should include:

- unit: literal-false throwing arm is effectless; literal-true selected throwing arm still throws;
- unit: throw after `return`/`continue` is unreachable and does not activate catches;
- unit: a reachable attempt throw still activates the handler and preserves the existing negative;
- driver compile/run: the `nothrow` literal-false shape;
- driver compile/run: the permanently divergent loop with an unreachable catch-side `break`.

The existing deliberately conservative rule for typed non-catch-all arms is a separate v1 policy and is not challenged by this finding. This finding is only about CFG paths that cannot execute at all.

### 2. P1 — the new scheduler is not a fixed point over thunks and stage-2 hidden lambdas

**Status: Confirmed structural omission; the proposed source repros need focused execution.**

The relevant producer order in `lang/driftc/driftc.py` is:

1. hidden-lambda specs are drained and harvested through `lower.hidden_lambda_specs()` in the earlier worklist (notably around lines 6406 and 7437-7438);
2. generic instantiations and late wrappers are drained/synthesized around lines 7534-7596;
3. `type_checker.thunk_specs()` is synthesized once at lines 7609-7638;
4. the captureless-lambda loop starts at line 7650.

Revision 4 correctly adds `typed_fns_by_id[spec.fn_id]`, `_queue_instantiations()`, `_drain_instantiations()`, and `_synthesize_late_drained_fns()` to the last loop. But work done inside that loop can produce two kinds of spec whose consumers have already finished:

#### 2a. A lambda recheck can register a new thunk after the one-shot thunk loop

Function-reference coercion can call `_ensure_ok_wrap_thunk()` / `_ensure_boundary_thunk()` and append to `self._thunk_specs` at `lang/driftc/type_checker.py:4462-4502`. If the function reference is first typed while a newly discovered lambda spec is rechecked in the captureless drain, the thunk is registered after lines 7609-7638. The captureless quiescence step never revisits `type_checker.thunk_specs()`, so HIR/MIR may reference a thunk function that was never synthesized.

A proposed driver shape is an uninvoked outer lambda containing an unannotated, uninvoked middle lambda whose body coerces a `nothrow` named function to a throwing `Fn() -> Int` function value:

```drift
fn target() nothrow -> Int {
    return 1;
}

pub fn main() nothrow -> Int {
    val outer = || nothrow => {
        val middle = || nothrow => {
            val fp: Fn() -> Int = target;
            0
        };
        0
    };
    return 0;
}
```

On the current pending-map snapshot route, `outer` is emitted from the user-function flush; `middle` is first finalized while rechecking `outer`; its function-reference coercion is therefore a candidate for post-thunk-loop production. K should confirm the exact inferred throw modes and adjust only the annotations needed to force `ThunkKind.OK_WRAP`.

#### 2b. Lowering a captureless spec can produce a hidden lambda after the hidden-lambda worklist

The captureless loop constructs `HIRToMIR` and calls `_lower_lambda_block()` at `lang/driftc/driftc.py:7760-7802`, but unlike the earlier lowering loops it never consumes `lower.synth_sig_specs()` or `lower.hidden_lambda_specs()`. Stage 2 appends those specs when it lowers immediate lambdas and callback lambdas at `lang/driftc/stage2/hir_to_mir.py:5655-5656` and `5921-5922`.

Therefore a captureless stored lambda whose body contains an IIFE can emit an `M.Call` to a newly allocated hidden function while that hidden function's spec is discarded with the local `lower` object. A minimal proposed compile/run boundary is:

```drift
pub fn main() nothrow -> Int {
    val outer = || nothrow => {
        (|| nothrow => { 42 })()
    };
    return 0;
}
```

`outer` is not lowered as part of `main`; it is lowered only in the captureless worklist, after the hidden-lambda drain. The inner IIFE is exactly the stage-2 producer that the captureless loop currently does not harvest. A callback-boxing companion would protect the second producer site if it is source-reachable in this context.

**Proposed closure:** use a joint scheduler with seen sets/indexes for at least captureless lambda specs, hidden lambda specs, and thunk specs, and interleave generic-instantiation/wrapper synthesis until none of those producers adds work. Every rechecked typed function should retain the Revision 4 registration/instantiation steps; every HIR-to-MIR lowering should harvest `synth_sig_specs()` and `hidden_lambda_specs()` before checking quiescence. Merely moving the existing thunk or hidden pass later is unlikely to be total because hidden-lambda checking and generic instantiation can themselves create further function work.

K may replace this proposed structure if another existing owner already guarantees either spec is emitted. To rebut the finding, that owner needs to be identified after the captureless loop and shown to consume specs produced by these exact local `type_checker`/`lower` instances; no such consumer is present in the reviewed tail before MIR validation.

### 3. P1 — the “discovered during drain” regression is resolved before the drain

**Status: Confirmed from test source and pending-lambda routing.**

`test_nested_spec_with_generic_call_discovered_during_drain_runs` at `lang/tests/driver/test_uninvoked_stored_lambda.py:162-179` says the inner spec is first discovered while the drain rechecks the outer spec. Its source instead ends with:

```drift
val outer = | | nothrow => {
    val t: Fn() -> Int = || -> Int => { (ident(41) + 1) };
    0
};
val x = outer();
```

`outer()` resolves and types the pending outer lambda during the original `main` check. Inside that check, `t` has an explicit expected function type, so its lambda is typed and registered through the ordinary annotated `HLet` path. Both specs are consequently available before `driftc.py` snapshots/drains `lambda_fn_specs()`. The test is a useful nested-generic compile/run positive, but it does not exercise dynamic worklist production, parent registration for a newly produced spec, or the quiescence branch added in Revision 4.

**Proposed replacement/companion:** leave the outer lambda uninvoked and make the inner binding unannotated so the first user-function pending snapshot includes only the outer lambda. For example:

```drift
fn ident<T>(x: T) -> T {
    return x;
}

pub fn main() nothrow -> Int {
    val outer = || nothrow => {
        val middle = || nothrow => { ident(41) + 1 };
        0
    };
    return 0;
}
```

On the current route, typing `outer` creates a new pending `middle` after the user-function flush has taken its `list(...)` snapshot. Rechecking `outer` as a standalone captureless spec then flushes/registers `middle`, making it a real during-drain producer. A compile/run test protects emission even though neither lambda is called. Combining this shape with the thunk and hidden-lambda cases in Finding 2 would give the closure claim meaningful boundary coverage.

### 4. P2 — implicit borrowed captures are compared as strings, so the borrowed diagnostic is unreachable

**Status: Confirmed representation mismatch.**

The Revision 4 flush combines implicit captures and explicit HIR capture entries, then checks:

```python
any(getattr(c, "kind", None) in ("ref", "ref_mut") for c in _all_caps)
```

at `lang/driftc/type_checker.py:13720-13721`.

Those two lists do not use one representation:

- `discover_captures()` returns `closures.HCapture`, whose `kind` is `HCaptureKind.REF` / `HCaptureKind.REF_MUT` (`lang/driftc/stage1/closures.py:17-25`);
- `HExplicitCapture.kind` is the string representation (`lang/driftc/stage1/hir_nodes.py:317-354`).

An ordinary implicit read defaults to `HCaptureKind.REF` in `capture_discovery.py`, so the string membership test is false. The flush still rejects safely, but it emits the generic “capturing lambdas cannot be coerced to function pointers” message instead of Revision 4's claimed borrowed-capture diagnostic. The same enum/string mismatch already exists in the ordinary expected-function route at `type_checker.py:7889`; this is a pre-existing diagnostic bug that Revision 4 copied into the new authority.

The new implicit-capture test at `test_uninvoked_stored_lambda.py:116-128` actually pins the generic message, while the explicit companion uses `captures(copy x)`, so neither test covers implicit `REF`/`REF_MUT` classification.

**Proposed closure:** normalize capture kinds through one helper that accepts both `HCaptureKind` and `HExplicitCapture.kind`, and use it in the ordinary function-pointer rejection and pending flush. Add implicit shared/mutable-borrow cases plus an explicit `&`/`&mut` companion if those surface forms are legal. Keep the existing single-diagnostic/no-cascade assertions.
