## P1 — broad exception suppression creates a false user diagnostic

At `call_resolver.py:6866-6874`, the ordinary-owner probe calls
`MethodRegistry.get_free_candidates(...)` inside:

```python
try:
	...
except Exception:
	_free_cands = []
```

`get_free_candidates` is a pure, stable lookup that returns a list; its
implementation has no expected failure mode. If registry state or visibility
plumbing is defective, the broad catch converts that compiler defect into
"there is no ordinary candidate" and can then emit the user-facing
`E-CTOR-EXPECTED-TYPE`. That is semantic masking and directly violates the
repository rule that internal/checker contract failures must not surface as
user errors.

Remove the broad catch and let unexpected failures propagate through normal
ICE containment. Prefer using the same `callable_registry` authority/local as
the later real free-call resolver so the probe and consumer cannot silently
diverge. No fallback to `[]` is appropriate here.

This is a narrow change, but the currently in-flight full driver result was
started before it. Stop it if still running and rerun the required focused
set plus `lang-driver-test` after the final patch; do not report the pre-patch
run as final evidence.
