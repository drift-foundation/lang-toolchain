## Findings

### 1. P1 — `HBreak` and `HContinue` are incorrectly classified as fallthrough

**Status: Confirmed statically.**

`_stmt_exits()` has no cases for `HBreak` or `HContinue`; both reach the default `{Exit.FALLTHROUGH}` at `lang/driftc/stage1/hir_flow.py:135-137`. The accompanying comment says they do not terminate the function, but the relevant question for this sequential block analysis is whether execution reaches the next statement in the same block. It does not.

This also makes `block_contains_reachable_break()` walk through a `continue`, because its reachability scan stops only when `_stmt_exits(stmt)` lacks `FALLTHROUGH`. For example:

```drift
loop {
    continue;
    break; // unreachable
}
```

The helper currently reports the `break` as reachable and therefore gives the loop a `FALLTHROUGH` exit. A non-`Void` lambda whose actual body is permanently divergent can consequently be rejected. An unreachable bare return after `continue` can likewise be added to the exit set and produce a false missing-value rejection.

The downstream implementation confirms that both statements terminate their current path: `_visit_stmt_HBreak` and `_visit_stmt_HContinue` emit gotos in `lang/driftc/stage2/hir_to_mir.py:9775-9804`.

**Proposed closure (the implementer should validate the model):**

- Represent `HBreak` and `HContinue` as no ordinary block exit—most likely `frozenset()`—rather than `FALLTHROUGH`.
- Keep reachable-break discovery separate: a reachable `HBreak` is detected before its empty exit set stops the scan; a `continue` stops the scan before later unreachable statements.
- Add unit pins for `continue; break`, `continue; return;`, and a reachable `break`.
- Add a source boundary regression for the divergent non-`Void` lambda and a full compile/run companion, because this acceptance decision is lowering-visible under AGENTS.md Rule 3.

This behavior appears inherited from the old analysis, but it is now part of the claimed shared authority and is directly exercised by this change, so it should be closed here rather than preserved.

### 3. P2 — catch-all `try` retains a caught body `THROWS` exit

**Status: Confirmed statically as an exit-set precision/contract issue; no incorrect current accept/reject case established.**

The `HTry` branch in `_stmt_exits()` unions the try body's exits with all catch-arm exits. When a catch-all is present, a `THROWS` exit from the body is handled and does not escape the try statement, yet it remains in the returned set.

The current consumers primarily ask whether `FALLTHROUGH` is present or whether all exits are throws, so I did not establish a current user-visible failure from this over-approximation. It nevertheless contradicts the new module's role as the shared authority for the ways a block can actually exit and could mislead later consumers.

**Proposed closure:** when a real catch-all handles the body exception path, remove the body's `THROWS` member before unioning catch exits; preserve it when no catch-all exists. Add focused unit cases for caught body throws and throws originating in a catch arm. K should confirm the precise `HTry`/catch representation before applying this formulation.
