# Static review: fast-or-fail promotion, revision 1

Timestamp: 2026-08-05T21:27:46Z

The overall verify-candidate/promote-install split is right, and the removal of the fixture-reproduction pass is clear. This revision is not ready for the production smoke yet. I found three blocking contract gaps and a stale-contract sweep that needs to land before verify creates the final candidate. Slawomir has approved the corresponding test edits.

## P1 — promote can still compile the runtime archive

`run_promote()` calls `_toolchain(extra)` at `tools/drift_corpus_check.py:847`. That reaches:

```text
_fp.toolchain_fingerprint
  -> collect_toolchain_components
  -> prebuild_runtime
  -> build_runtime_archive
```

`build_runtime_archive()` invokes clang/ar whenever the archive is absent or `_needs_rebuild()` considers it stale. The existing synthetic zero-compile pins only observe `Harness.compiles`, so they prove that fixtures are not compiled but do not detect this runtime compilation path.

That violates the approved fast-or-fail rule: promotion must not build anything. Recompute current identity through a passive path which hashes/resolves the already-existing runtime artifact without calling the production build authority. If the required artifact is missing or cannot be validated, promotion should fail and request a new verify; it must not rebuild it. K should independently choose the cleanest factoring, but avoid weakening verify's existing prebuild-before-fingerprint authority.

Add a boundary pin which makes the runtime-build authority explode if promote reaches it, and prove promote still succeeds from a valid candidate/current existing-artifact setup. Also pin the missing/current-runtime-artifact case as a controlled failure with the baseline byte-identical and no build call.

## P1 — the embedded full snapshot is not fully validated

`_validate_handoff()` currently checks only that the snapshot and embedded toolchain composites look like 64-byte hex strings. It does not validate the exact run-snapshot/toolchain key sets, component shapes, embedded composite, or recomputed run-snapshot composite, although the centralized authority already exists as `_fp.validate_fingerprint()`.

Call that authority while validating the candidate, catch its `ValueError`, and return a controlled candidate diagnostic before current-tree work or staging. The current `_valid_handoff()` unit helper uses a deliberately abbreviated snapshot and will need to be converted to a genuinely valid full snapshot. Add a resealed nested-tamper case (for example a changed toolchain component with the old composite, or a missing snapshot key) proving candidate rejection before staging/baseline mutation.

Staging validation happens to catch many such corruptions later today, so the live baseline is generally protected, but that is not the promised complete candidate validator and it unnecessarily performs current-tree work before discovering candidate damage.

## P1 — invalid run metadata can be installed

The `run_meta` shape accepts booleans for `started_unix`/`duration_s`, non-finite JSON numbers, negative duration, and nonpositive jobs. Unlike the malformed snapshot case, `_read_baseline()` does not validate `metadata.json`, so a resealed candidate can install these values into the live baseline and pass post-install validation.

At minimum require non-boolean finite numeric `started_unix > 0`, finite `duration_s >= 0`, `jobs > 0`, and nonempty string metadata fields. Whether repo-root/Python values should be cross-checked against current identity or deliberately remain historical verify provenance is K's design call; do not accidentally reject a valid delayed promotion merely because a checkout was moved. Pin malformed values through `run_promote()` with zero baseline mutation, not only the direct validator.
