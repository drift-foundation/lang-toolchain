  Compiler/Package Boundary Architecture Review

  1. Current-State Map

  What the "world" is today

  Where source and package paths diverge

  The temporal split. The parser creates a fresh TypeTable and resolves all type references into TypeIds. Then — after parsing is complete — the linker imports package
  types into the same TypeTable, potentially changing what nominal lookups return. This creates two eras of TypeIds:

  - Parser-era TypeIds: Assigned during parsing, before package types are fully loaded. Cross-package type references that aren't covered by pre-population hacks become
  FORWARD_NOMINAL placeholders.
  - Post-link TypeIds: Assigned during import_type_tables_and_build_typeid_maps. These are the canonical TypeIds for package types.

  The bridge between these eras is a series of canonicalization sweeps that chase down FORWARD_NOMINALs and patch them. I count at least five separate sweep sites:

  1. Parser's _coerce_forward_nominal (parser/init.py ~line 3863)
  2. Linker's post-link FORWARD_NOMINAL resolution (type_table_link_v0.py ~line 1164)
  3. _canonicalize_signature_type_ids on base signatures (driftc.py)
  4. _canonicalize_signature_type_ids on external signatures (driftc.py)
  5. _canonicalize_mir_type_ids during MIR lowering (driftc.py ~line 330)

  Each sweep is a symptom of the same root problem: the parser committed to TypeIds before the full type universe was available.

  Pre-population hacks. To mitigate the temporal split, the driver extracts data from loaded packages BEFORE calling the parser and injects it via special parameters:

  ┌────────────────────────────┬────────────────────────────────────────┬────────────────────────────────────────────────────────────────────────────────────────────┐

  │ external_type_aliases      │ Package type aliases decoded from      │ Without it, resolve_opaque_type during signature resolution creates wrong TypeIds for      │
  │                            │ payload JSON                           │ aliased cross-package types                                                                │

  ├────────────────────────────┼────────────────────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────┤

  Each of these is a partial, ad-hoc extraction of data that the linker will process more thoroughly later. They exist because the parser runs before the linker.

  2. Target-State Proposal

  The canonical semantic store

  Promote the TypeTable into a SemanticWorld — a single object that owns all cross-cutting semantic data currently split across TypeTable, CallableRegistry,
  module_exports, and FnSignature collections:

  SemanticWorld
  ├── types: TypeStore (current TypeTable core — TypeIds, TypeDefs, nominal index)
  ├── aliases: AliasStore (module-scoped type aliases, currently in TypeTable.type_aliases)
  ├── callables: CallableStore (current CallableRegistry — methods, free fns)
  ├── schemas: SchemaStore (struct/variant/interface schemas, exception schemas)
  ├── modules: ModuleStore (exports, imports, reexports, module→package ownership)
  └── signatures: SignatureStore (FnSignature by FunctionId)

  The key principle: all ingress paths (source parsing, package loading) write to the same SemanticWorld through the same API. No pre-population hacks. No post-link
  canonicalization sweeps. No FORWARD_NOMINAL escape hatch for cross-package types.

  TypeId remains a session-local primary key

  TypeId stays as an opaque integer — it's a fast lookup key into the SemanticWorld. But:

  - TypeIds are assigned ONCE, during ingress, and never remapped.
  - Stable cross-boundary identity uses NominalKey (package_id, module_id, name, kind) — never raw TypeIds.
  - Package serialization stores NominalKeys; deserialization maps them to session-local TypeIds through the SemanticWorld's nominal index.

  Aliases as first-class metadata

  Aliases remain in the SemanticWorld as API/DX metadata. But:

  - Canonical equality uses resolved TypeIds, not alias names. Two types are equal iff they have the same TypeId.
  - Alias resolution happens at ingress time, not during type checking. By the time the checker runs, all alias references have been resolved to their canonical TypeIds.
  - Alias metadata is preserved for diagnostics, error messages, and API surface documentation, but it never affects equality or matching.

  Provenance as data, not branching

  Each entry in the SemanticWorld carries a provenance field:

  enum Provenance:
      Source(module_id, file_path)
      Package(package_id, module_id)

  Checker/lowering/codegen never branch on provenance. It exists only for diagnostics, error reporting, and package emission.

  3. Ingress Model

  Phase 1: Package Loading → SemanticWorld

  Before any source parsing, load all packages and populate the SemanticWorld:

  1. Discover and load package files (existing code, unchanged)
  2. For each loaded package:
    - Import all nominal types (structs, variants, interfaces) into types
    - Import all type aliases into aliases
    - Import all struct/variant/interface schemas into schemas
    - Import all exception schemas into schemas
    - Import all signatures into signatures
    - Import all module exports/reexports into modules
    - Register all methods/callables into callables
  3. Mark the SemanticWorld as "packages loaded" — all package data is now available

  This is essentially what import_type_tables_and_build_typeid_maps + _register_signatures_in_callable_registry(external) + collect_external_exports do today, but done
  BEFORE the parser runs.

  Phase 2: Source Parsing → SemanticWorld

  The parser receives the SemanticWorld (already populated with package data) and adds source types to it:

  1. Pre-declare all source nominal types (existing code, unchanged)
  2. Lower each source module, resolving type references via resolve_opaque_type which now has the FULL type universe available
  3. Register source methods/callables into the same callables store
  4. Build source module exports into the same modules store

  No FORWARD_NOMINAL needed for cross-package types. No pre-population hacks. No post-link canonicalization sweeps.

  Common ingress contract

  Both package loading and source parsing call the same SemanticWorld API:

  world.types.declare_struct(module_id, name, type_params) -> TypeId
  world.types.declare_variant(module_id, name, type_params) -> TypeId
  world.aliases.define(module_id, name, type_params, target) -> None
  world.schemas.define_struct_fields(type_id, fields) -> None
  world.callables.register_method(impl_target, name, signature) -> None
  world.modules.set_exports(module_id, exports) -> None

  No separate code paths. No is_external flags. No skip_modules parameters.

  - No new TypeIds are allocated (except for structural types like Ref<T>, Array<T> which are interned on demand)
  - No new aliases are registered
  - No new methods are registered
  - resolve_opaque_type only looks up existing types, never creates FORWARD_NOMINALs

  6. Migration Plan

  Stage 0: Preparation (no behavioral change)

  Extract SemanticWorld interface. Create a SemanticWorld class that wraps the existing TypeTable. Initially it's just a thin wrapper — all existing callers still use
  TypeTable directly. This establishes the target API surface without changing any behavior.

  - Add lang/driftc/core/semantic_world.py
  - SemanticWorld holds a TypeTable, exposes the same methods
  - No callers changed yet

  Stage 1: Move package ingress before parser (the key structural change)

  Goal: Eliminate the temporal split by running type table linking BEFORE the parser.

  1. In driftc.py:main(), move import_type_tables_and_build_typeid_maps (currently at line 8150) to BEFORE the parse_drift_workspace_to_hir call (line 7979).
  2. Pass the already-populated TypeTable to the parser instead of letting it create a fresh one.
  3. The parser's parse_drift_workspace_to_hir receives a TypeTable with all package types already present.
  4. Remove the external_type_aliases parameter and pre-population hack.
  5. Remove the external_exception_schemas parameter and pre-population hack.
  6. Remove the parser's _coerce_forward_nominal sweep (no FORWARD_NOMINALs for package types).

  This is the highest-leverage single change. It eliminates the root cause of the recent bug pattern.

  Risk: The parser currently creates its own TypeTable and returns it. Changing it to accept an external TypeTable may surface assumptions about TypeId allocation order.
   Regression coverage: all existing package-consumer tests + the new cross-package alias tests.

  Stage 2: Unify method/callable registration

  1. Move external signature reconstruction (driftc.py lines 8222-8509) to happen alongside package type ingress (Stage 1).
  2. Register package callables into the CallableRegistry BEFORE the parser runs.
  3. The parser can then see package methods during type checking without a separate registration phase.
  4. Remove the is_external and skip_modules parameters from _register_signatures_in_callable_registry.

  Stage 3: Eliminate FORWARD_NOMINAL for package types

  1. After Stage 1, ensure_named should never create FORWARD_NOMINALs for package types (they're already declared).
  2. FORWARD_NOMINAL remains only for source-internal forward references (struct A references struct B in the same workspace before B is declared).
  3. Remove _canonicalize_signature_type_ids (no longer needed).
  4. Remove _canonicalize_mir_type_ids (no longer needed).

  Stage 4: Promote SemanticWorld to primary interface

  1. Move CallableRegistry into SemanticWorld.
  2. Move module exports into SemanticWorld.
  3. Move FnSignature storage into SemanticWorld.
  4. All phases (parser, checker, lowerer, codegen) receive SemanticWorld instead of separate TypeTable + CallableRegistry + signatures + exports.

  Stage 5: Add world-freeze boundary

  1. After all ingress is complete (packages + source), call world.freeze().
  2. After freeze, declare_struct/define_type_alias/register_method throw if called.
  3. Only structural type interning (ensure_ref, ensure_function, new_array) remains allowed.

  7. Risks / Pushback

  The direction is correct

  The recent bug pattern — alias resolution before linking, callback inference without expected types, method registry TypeId mismatch — all trace back to the temporal
  split between parser-era and post-link-era TypeTables. Moving package ingress before parsing is the right structural fix.

  Stage 1 is the critical path

  Stages 2-5 are important but can be done incrementally over weeks. Stage 1 (move linking before parsing) is the one change that eliminates the root cause. If we only
  do one thing, do Stage 1.

  Risk: TypeId allocation determinism

  The current system guarantees deterministic TypeId allocation within a single compilation. If we change the allocation order by doing package linking before parsing,
  TypeIds will change. This could affect:

  - Package serialization (TypeIds are stored in package payloads). Package
    signatures still carry raw param_type_ids / return_type_id /
    impl_target_type_id and are reconstructed via tid_map remapping.
    NominalKeys provide stable nominal identity, but the signature payload
    contract still depends on remapped integer ids.  Full migration to
    semantic type expressions is deferred to Phase 8.
  - Test assertions that check specific TypeId values. Mitigation: no tests should depend on specific TypeId integers.

  Risk: Circular dependency between parser and linker

  The parser needs the TypeTable to resolve types. The linker needs the TypeTable to import into. Today they're sequential. If we move the linker before the parser, the
  linker populates the TypeTable first, then the parser adds to it. This should work — the linker creates the TypeTable, the parser enriches it — but it inverts the
  current ownership model where the parser creates the TypeTable.

  What I would NOT do

  - Full rewrite. The TypeTable internals are sound. The nominal index, schema storage, and instance caching work correctly. The problem is phase ordering and the escape
   hatches built around it, not the core data model.
  - Merge TypeTable and CallableRegistry. They serve different purposes (type identity vs. call resolution). They should live in the same SemanticWorld wrapper but
  remain separate internal stores.
  - Remove FORWARD_NOMINAL entirely. It's still needed for source-internal forward references within a workspace. The goal is to eliminate it for cross-package types,
  not for all types.
