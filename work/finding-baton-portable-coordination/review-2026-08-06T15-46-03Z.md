Reviewer hypothesis: YES, central transactional metadata is now the smaller design, but use SQLite (Python stdlib sqlite3) rather than inventing a whole-file JSON database plus flock. The current proposal has accumulated REPLYING, CLOSING, RECOVERING-CLAIM, transaction intents, published tombstones, temps, GC classes, NAME_MAX budgets, and multi-entry crash protocols. That is a custom database/WAL expressed through filenames.

Candidate SQLite authority:
- instance directory remains explicit/self-contained: baton.json, instance.json, mailbox.sqlite3 (+ SQLite-owned WAL/SHM), optional wakeup artifact; no filename-routed message authority;
- protocol 6 is the SQLite schema/state contract; config remains strict JSON and explicitly passed;
- normalized tables own messages, state, participant/actor/seed claim ownership, replies/responds_to, notices, notice_seen, recovery records/reasons, and optionally an append-only transition/event ledger;
- claim = conditional UPDATE pending→claimed in BEGIN IMMEDIATE, rowcount=1 single winner;
- reply = ONE DB transaction that verifies claimed owner, inserts the fixed outgoing response/body/reference, and marks the incoming claim completed; no REPLYING state and no duplicate-retry window;
- content-bearing close = ONE DB transaction recording the final disposition and completing the incoming claim;
- recover-claim = ONE transaction recording recovery identity/reason and claimed→pending; no intermediate recovery state;
- expire notice + delete seen rows = ONE transaction;
- transient bodies live in the DB; existing/Baton-created durable details remain external hash-pinned references. External detail is committed/fsynced FIRST, then the DB transaction publishes its reference; crash can leave only an unreferenced detail, never a visible missing reference;
- use WAL (or challenge journal mode), foreign_keys=ON, synchronous=FULL, busy timeout, explicit transactions, local-filesystem-only checks, integrity_check/doctor, and schema/user_version validation;
- wait must retain real-time UX: investigate a correct query-before-arm/requery-after-arm inotify strategy watching DB/WAL directory plus defensive polling, so commits cannot be missed; no daemon;
- gc becomes bounded SQL over terminal/expired rows plus external-detail orphan reporting. Recovery redelivers the same committed row/ID; it never recreates content/direction;
- strict dirfd/no-follow still applies to instance/config/external roots/details. SQLite owns its internal files.

Compare against a single canonical JSON metadata file guarded by a never-renamed flock inode and atomic whole-file replace. Address why SQLite is or is not preferable for locking, crash recovery, scale, corruption blast radius, auditability, human inspection, standard-library/zipapp availability, read-only distribution, and local-filesystem semantics.
