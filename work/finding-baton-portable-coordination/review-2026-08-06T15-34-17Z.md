LOCKED RULINGS

1. Python floor: Python 3.11 minimum. The zipapp's tiny __main__ bootstrap must itself parse on a pre-3.11 interpreter, test sys.version_info before importing v6 modules, and exit 2 with a clean diagnostic.

2. Dead notice-seen receipt GC: add an explicit safe gc operation. It may delete only strictly valid notice-seen receipts whose uniquely named notice is absent. Notice names are never reused, so such receipts cannot become live again. Malformed/ambiguous receipts remain untouched and doctor-reported. doctor itself stays read-only. GC does not impersonate or re-prove the missing notice author because it removes derived state only.

3. Dead-seed claim recovery: a dead seed means a CLAIMED directed handoff whose owning actor instance is confirmed gone; NOTICE broadcasts remain non-claimable. No age-based stealing or automatic timeout. Add a human-authorized explicit recovery ceremony that validates the exact claim/envelope/reference and atomically returns an ordinary abandoned CLAIMED handoff to its original PENDING name, followed by mailbox-directory fsync. Require an explicit reason and warning that the former owner must be quiesced/dead.

4. Strict JSON: every protocol JSON surface (config, instance stamp, envelopes, receipts, transaction intent, schema tests) rejects duplicate keys, comments/trailing content, NaN/Infinity, unknown fields, wrong types (including Bool where Int is required), malformed addresses, and unsupported versions before canonicalization. Config digest is over canonical UTF-8 JSON of the entire validated object: sorted keys, compact separators, finite values only.

5. Durability/visibility: Baton is a mini filesystem database. Success means the transition is atomically visible and durably committed, assuming a supported local filesystem honors fsync/rename. Creation = sibling temp opened exclusive/no-follow, complete write, file fsync, no-clobber final rename, containing-directory fsync. Deletion = validated exact unlink then directory fsync. Claim/state rename = no-clobber rename then directory fsync. Cross-filesystem durable handoff ordering remains detail commit first, envelope commit second; a crash may leave an unreferenced detail but never a visible envelope pointing at incomplete content. instance.json/receipts/transaction records follow the same commit discipline.

6. Directory-anchored operations: open instance/mailbox/receipts/configured roots as validated directory descriptors and perform child operations through dirfd/openat/renameat2-style APIs with no-follow semantics. Resolve references with openat2 RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS where supported and a component-by-component O_NOFOLLOW containment fallback. Do not validate a pathname and later reopen it through an unanchored mutable path.

7. Crash injection: Phase-3 tests deterministically terminate subprocesses at every durable transition boundary (temp write, file fsync, rename, dir fsync, response publication, incoming-state removal, notice unlink before receipt cleanup, regen commit). Reopen with a fresh process and prove only old/new valid states, no partial final JSON, correct orphan reporting/GC, and idempotent recovery. Prefer injected storage-layer fault hooks in tests over an ambient production CLI environment switch. Real power-loss guarantees remain bounded by honest filesystem fsync semantics.

8. Versioning: tool version is independent SemVer major.minor.patch; protocol version is a simple single integer, initially 6. Patch = implementation fix with unchanged CLI/state/protocol; minor = backward-compatible tool/CLI feature within protocol 6; major = breaking tool CLI/config/distribution behavior; protocol increments only for breaking mailbox/envelope/state format. Self-report and DISTRIBUTION manifest carry tool_version, protocol_version, and python_min. Reviewer recommends initial portable Baton tool 1.0.0; challenge only if a concrete version-history reason supports another start.

NEW REPLY CRASH CONTRACT — REDELIVERY, NEVER RE-CREATION

A crash after publishing a response but before removing the incoming claim must never cause a retry to generate a second response or reinterpret the work. Intentional multiple messages remain valid stream events; this rule is only for recovery of ONE interrupted reply/close transition.

Before entering the intermediate state, Baton durably persists the complete, immutable outgoing reply intent under a fixed response_id: exact recipient/routing metadata plus either the embedded transient body or the hash-pinned durable reference. Then it atomically transitions CLAIMED-* to a flat mailbox REPLYING-*-WITH-<response-id> state and fsyncs the mailbox directory. It publishes that exact response idempotently, then removes REPLYING and fsyncs.

REPLYING is transaction state, never claimable work:
- normal wait skips it; scan/doctor report owner actor/seed, start time, response_id, and recovery state;
- the original actor/seed may resume and finish it;
- if the seed is confirmed dead, a human-authorized recover-reply lets another actor finish delivery of the ALREADY-PERSISTED intent;
- recovery accepts no new response body, direction, kind, recipient, outcome, or reference;
- if the outgoing response is already present or has advanced, recovery verifies the fixed identity/content and completes cleanup rather than publishing a new logical message;
- once CLAIMED has become REPLYING, recovery completes the reply and never returns the request to PENDING, because the response may already have become visible or been consumed.

This is effectively-once logical publication implemented through idempotent at-least-once redelivery. The intermediate reply-intent storage and response identity must remain discoverable long enough to prove completion even if the outgoing transport token has already been claimed/consumed. Challenge the smallest correct representation (transaction record, deterministic retained detail/identity, or another design), but not the invariant: recovery redelivers fixed work/direction/content and never recreates them.
