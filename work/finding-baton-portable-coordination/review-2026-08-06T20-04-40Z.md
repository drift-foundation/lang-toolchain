## P1 — `_resides_at_route()` follows route symlinks and does not bind directory identity

`_resides_at_route()` calls `os.stat(dirname(route_config))`. Unlike `_open_dir_no_follow()`, this follows a substituted ancestor symlink. A source-role copy can therefore make the stored source route resolve to its own directory, pass the source-only guard, and abort. Restoring the original source path then lets the true source abort too.

Deterministic repro against the frozen 173-test pair:

1. enter/copy; copy the unbound destination pair to a rogue directory;
2. delete the bound destination, making the destruction attestation true;
3. rename the real source directory aside and replace its old path with a symlink to the rogue directory;
4. call `abort_move()` on the rogue copy — it succeeds because `os.stat(source_parent)` follows the symlink;
5. remove the symlink, restore the real source directory to its path, and abort the true source.

Observed result:

`symlink_route_two_active {'aborted': True} {'aborted': True} ['source', 'rogue']`

This violates both the single-authority promise and the explicit component-walk/no-follow contract.

Do not repair this with another following pathname comparison. Bind the identities of the already-open source and destination directories at `maintenance_enter(move=True)` (at least stable `{st_dev, st_ino}` plus canonical config path/basename), and validate later through held/opened no-follow dirfds. A route must satisfy all of:

- canonical path equals the committed route;
- `_open_dir_no_follow(parent)` succeeds and its identity equals the identity bound at enter;
- the current Store's held `dirfd` has that same identity;
- config basename matches.

This must apply symmetrically to source copy/decommission/abort and destination bind/activate, including committed retry fast paths. Add the exact symlink repro and a directory-replacement/rename negative for each role.

## Prefer one immutable move-binding authority

The latest handoff says both routes are retained in immutable history, but the schema still retains only `ceremonies.peer` (the destination). `move_source` exists only in mutable `instance_meta`; destination activation clears it, and `move_status_inspect()` does not return it. The source route and both bound directory identities therefore disappear from the active destination's audit state.

Rather than continuing to add optional ceremony columns and live-state checks, consider an immutable `moves` row keyed by token, created in the maintenance-enter transaction and copied with the DB:

`{token, instance_uuid, source_config, source_dev, source_ino, destination_config, destination_dev, destination_ino, created_ts}`

Every role transition and committed retry can consult that one authority; ceremonies remain the event log. Equivalent normalization is fine if you find a better model, but both routes and identities must survive activation and be immutable. Pin schema immutability and exact-route/identity checks. This is a design recommendation based on the repeated failure shape, not a mandate to use that table name or exact columns.
