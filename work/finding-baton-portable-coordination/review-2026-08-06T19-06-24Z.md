## P1 findings

1. **Reply retry compares optional routing as a wildcard instead of comparing its effective defaults.**

   On first publication, `recipient=None` means the incoming sender and `thread_id=None` means the incoming thread. On retry, `_verify_retry()` skips each comparison when the caller again supplies `None`. That makes the same input mean “inherit” on the first call but “do not validate” after commit.

   Repro: incoming route is reviewer / `t1`; first reply explicitly commits to lead / `t2`; retry omits both overrides. Current result is `already_committed=True` and redelivery of the lead/`t2` response, although the retried operation's effective route is reviewer/`t1`.

   Normalize `effective_recipient` and `effective_thread` from the incoming row before disposition lookup, pass both unconditionally to retry validation, and validate participants only on the fresh-publication path so a historical retry remains possible after a safe config removal. Add first-explicit/retry-omitted negatives for recipient and thread, plus first-default/retry-omitted positives. This mirrors the effective-retention correction already made.

2. **Terminal state and terminal timestamp are only coupled in one direction.**

   The `BEFORE UPDATE OF completed_ts/terminal_ts` triggers prevent changing a timestamp without an edge, but the reverse is open: a context-bearing direct update can perform `messages claimed→completed` without mentioning `completed_ts`, and `claims active→completed` without mentioning `terminal_ts`. Both commit. The resulting rows are `completed/NULL` and `completed/NULL`. Birth guards likewise do not forbid a pending/active row born with a prefilled terminal timestamp.

   Enforce the row shape in both directions, preferably with table CHECKs so every final row satisfies:

   - message pending/claimed ⇔ `completed_ts IS NULL`; message terminal ⇔ non-NULL;
   - claim active ⇔ `terminal_ts IS NULL`; claim completed/recovered ⇔ non-NULL.

   Existing edge/frozen-timestamp triggers can remain as immutability diagnostics. Pin both missing-timestamp terminal transitions and prefilled-timestamp births; keep the normal reply/close/recovery paths green.

3. **GC cannot collect a consumed reply chain because the two reply links form a deletion dependency the row-at-a-time loop does not account for.**

   Repro: transient message A is claimed and replied to with transient message B; B is claimed and closed; advance time and call `gc()`. A is excluded because B has `responds_to=A`; B is selected, but deletion fails with `FOREIGN KEY constraint failed` because A's disposition still references B through `response_message_id`. The whole GC transaction rolls back, so repeated runs cannot make progress.

   Resolve this at the retention-graph level rather than suppressing the FK. One plausible shape is: compute a removable transient component that is not anchored by a retained durable/recovery object; delete all dispositions/claims for that component first; delete messages child-before-parent; then delete their contents. If a durable parent's disposition anchors a transient response, define and pin whether that response metadata remains retained or whether the disposition contract changes while preserving retry identity. Please challenge this suggested algorithm if a smaller model preserves the same retention and retry guarantees, but the cyclic dependency needs an explicit contract.

   Required pins: all-transient reply chain; durable incoming + transient response override; transient incoming + durable response override; retry/ledger behavior on each side of GC; one GC call must either make its documented bounded progress or return cleanly, never abort on its own valid graph.

4. **The no-follow boundary protects only the final component of configured roots and the instance directory.**

   `_open_root_dir()` checks `path == normpath(path)` and calls one absolute `os.open(..., O_NOFOLLOW)`. Linux `O_NOFOLLOW` rejects only a symlink in the final component. A root such as `/tmp/base/link/leaf`, where `link` is a symlink and `leaf` is a real directory below its target, is accepted by `init_instance()`; the probe printed `intermediate_symlink_root accepted`. `open_instance_dir()` has the same ancestor-resolution seam.

   The approved boundary says directory-anchored/no-follow, not merely final-component no-follow. Walk canonical absolute directory components from an opened `/` dirfd using `O_DIRECTORY|O_NOFOLLOW|O_CLOEXEC` (or an equivalently pinned Linux `openat2` contract), keeping the next fd before closing the prior one. Use the same authority for the instance directory and configured roots. Add intermediate-symlink negatives for both; retain the existing final-symlink and attachment-descendant pins.

5. **`notice_seen` is mutable protocol state despite the handoff claiming immutability.**

   Only an insert-context trigger exists. An uncontextual `UPDATE notice_seen SET seed=...` succeeds, and an uncontextual `DELETE` succeeds, causing a live notice to be delivered again. The probe updated then deleted the receipt and observed zero rows. This can erase or rewrite who saw a broadcast.

   Add an unconditional update-abort trigger and restrict deletion to notice `expire`/`gc` context. Confirm that the FK CASCADE from those two operations still passes through the allowed context. Add direct update/delete negatives plus expiration/GC cascade positives. While touching these audit tables, add an insert-context/identity guard for `recoveries`: it is immutable after insertion today, but a raw uncontextual forged recovery row can still be born. If the intended trust boundary deliberately permits raw SQL writers, document and defend that instead; it would conflict with the surrounding fail-closed trigger design.

## P2 hardening required before filesystem/storage sign-off

6. **The attachment double-stat can be bypassed by a same-size rewrite with restored mtime.**

   The post-hash comparison checks only `(size, mtime_ns)`. At the existing `attach:post-hash` hook, rewriting `original` to same-sized `mutated!` and restoring the old mtime lets `send()` publish a pending attachment whose stored hash already disagrees with the file. `ctime_ns` changes and is the inexpensive missing detector. Compare at least `(dev, ino, mode, size, mtime_ns, ctime_ns)` across the held fd; the held fd prevents path/inode replacement but recording the full tuple makes the invariant explicit. Also open the leaf nonblocking or preflight it through an anchored descriptor so a FIFO/device cannot block before the regular-file rejection.

   Add a same-size/restored-mtime negative and a FIFO/non-regular-file nonblocking negative. The later claim-time hash check is useful defense in depth, but publication should not knowingly admit an already-ambiguous snapshot.
