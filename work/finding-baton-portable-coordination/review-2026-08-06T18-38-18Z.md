## P1 findings

1. **Maintenance/move/config gates are open-time checks, not transaction-time checks.** `_check_meta()` runs only in `open_instance()`. A `Store` opened before another process sets `maintenance=1` can subsequently call `_txn_begin()` and mutate the supposedly gated source. Empirical probe: two stores opened; store B committed `maintenance=1, move_status='moving'`; store A then successfully `send()`-published a pending message. The same stale-handle issue applies after `regen`: an already-open Store retains the old config policy/digest.

   Every write transaction must, after `BEGIN IMMEDIATE` and before setting operation context or mutating, re-read and enforce protocol, accepted generation/digest, maintenance, and move status against that Store's held config. Define narrow internal ceremony modes for regen/move/migrate instead of bypassing ordinary gating. Add stale-open-writer tests for maintenance, moved, and accepted-config change. Read/wait paths need an equivalent per-query gate later; an open-time boolean is not sufficient.

2. **Transient close content is retained.** `close_claim()` always inserts its supplied body into `contents`; `_scrub_transient_incoming()` deletes only the incoming message body. For a transient claim, closing with `body=b"should be transient"` leaves one live contents row and a disposition content reference. It also bypasses `TRANSIENT_BODY_MAX_BYTES`. This changes v5 transient semantics and contradicts PLAN T16.

   For a transient close, commit the disposition identity/hash/outcome but no retained body/content reference (or delete/null it within the same transaction). Enforce the transient cap before insertion. Pin transient close-with-body → zero retained content, hash-only retry identity, oversized rejection, and durable close-with-body retention.

3. **Config opening violates the approved no-follow boundary.** `load_config()` does `lstat(path)` and later ordinary `open(path)`. A replacement between those calls is followed. I deterministically replaced the checked regular config with a symlink in that window; `load_config()` loaded the symlink target (`config_race_loaded replacement`). Open the instance directory first, then open the config basename relative to the held dirfd using existing-only `O_RDONLY|O_NOFOLLOW|O_CLOEXEC`, `fstat()` the held fd, and read that fd. Reuse the same held directory identity for the DB open; do not re-resolve the config directory independently. Add replacement/symlink-race and config/DB-parent-binding pins.

4. **`_txn_begin()` can strand an open transaction.** Callers invoke `_txn_begin()` before entering their rollback-protected `try`. If `BEGIN IMMEDIATE` succeeds but the following `op_context` update fails, the exception escapes with `conn.in_transaction == True`. I pinned this by adding a rejecting trigger on `op_context`: `send()` raised `IntegrityError: break`, and the connection remained in a transaction. Make `_txn_begin()` roll back on every failure after BEGIN and normalize SQLite busy/damage errors consistently. Add a fault-injection test proving the Store remains reusable and context-null after each begin/commit boundary failure.

5. **The schema permits uncontextual destructive metadata changes.** `trg_msg_content_scrub_only` rejects only a non-NULL new value; `UPDATE messages SET content_id=NULL` succeeds in autocommit with no operation context, leaving an orphaned content row. `completed_ts`/`claims.terminal_ts` can likewise be rewritten independently of their state transition. The post-handoff file has acquired delete guards for later GC work, but those were not part of the handed-off/tested snapshot and do not close the content/timestamp holes.

   Require context plus the correct consuming/GC verb for content scrubbing, enforce old-non-NULL→new-NULL, and couple terminal timestamp changes to the legal state transition. Guard DELETE/GC paths and their final-ledger attribution in the same schema revision. Add direct-SQL negatives. Also enforce body XOR attachment as **exactly one** at both API and schema boundaries: current `send(body=None, attach=None)` succeeds (`bodyless_send ... None`), despite the locked XOR surface and v5's non-empty-message rule.

6. **Initialization is not a crash-atomic publication.** The final `mailbox.sqlite3` name is created first, `user_version` is written before the schema transaction, and a SIGKILL can leave a partial final DB which subsequent init refuses as “existing.” Normal exception cleanup does not prove crash safety. Initialize a unique scratch DB inside the instance directory, create schema + `user_version` transactionally, checkpoint/close/fsync and validate it, then atomically no-clobber publish the completed DB and fsync the directory. A crash may leave recognizable scratch, never a partial final authority. Use a private DB mode (normally `0600`, not current `0644`) unless the config explicitly defines a reviewed shared-user mode. Add kill/fault points across init and prove final state is absent-or-valid and retry-safe.

## P2 findings

7. **Retry comparison omits thread routing.** `_verify_retry()` checks recipient/kind/outcome/content but ignores a caller-supplied `thread_id`. A retry with different thread metadata is accepted as the old operation. Query the committed response's full routing tuple and fail closed on any supplied difference; a missing response row is integrity damage, not a case to skip validation. Add recipient, kind, thread, outcome, content, and reply-vs-close mismatch pins.

8. **Resolve response-retention behavior before CLI work.** v5 permits an explicit response retention override; the v6 method silently always inherits the incoming retention. The consolidated plan does not clearly authorize removing the override. Audit this surface and either preserve it with transaction/retention tests or request Slawomir's explicit ruling for the clean break. Do not let the CLI accidentally decide the contract.
