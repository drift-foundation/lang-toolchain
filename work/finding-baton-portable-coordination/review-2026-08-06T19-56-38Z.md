## P1 — “not at the destination” does not prove “is the true source”

`move_copy()`, `move_decommission()`, and especially `abort_move()` classify the true source as:

`move_role == 'source' and not store._resides_at(move_peer)`

But every unbound copy inherits `move_role='source'`, and every rogue location other than the one destination also satisfies “not at destination.” A source-role copy can therefore execute source-only ceremonies.

Independent repro against the frozen 167-test pair:

1. enter a move and `move_copy()` to the bound destination;
2. copy that still-unbound destination pair to a rogue directory;
3. delete the actual bound destination, so the `destination_destroyed=True` attestation is truthful;
4. `abort_move(rogue, token, destination_destroyed=True)`;
5. `abort_move(real_source, token, destination_destroyed=True)`.

Observed result:

`source_role_abort_two_active {'aborted': True} {'aborted': True} ['source', 'rogue']`

Both the original source and rogue copy accept ordinary writes. The post-bind destination route fix is correct, but source identity needs the symmetric binding.

Bind one canonical absolute **source config path** at `maintenance_enter(move=True)` alongside the destination path, and carry both routes in copied state and immutable move history. Source-only operations (`move_copy`, `move_decommission`, `abort_move`) must require physical residence at that exact source route; destination bind/activate must require the exact destination route. A copied/renamed source-role DB anywhere else must refuse all source-only ceremonies. Retain both routes for committed retry/audit after live fields clear.

Add red-first pins for a source-role rogue copy attempting:

- `abort_move` after the real destination has truly been destroyed (the exact two-active repro above);
- `move_decommission`;
- `move_copy`.

Then prove only the original source can abort/decommission/copy, while the bound destination remains the only activatable destination.

## P1 — source decommission does not require destination activation

`move_decommission()` currently accepts a source immediately after `maintenance_enter`, before a destination pair exists, is bound, or is activated. That can permanently mark the only authority `moved` and remove the normal `move_copy()` recovery path, contrary to the PLAN sequence “destination activation, then source decommission.”

Before decommissioning, validate the bound destination through a full no-follow open: same immutable UUID, committed `move_activate` for this token and both routes, active/non-maintenance state, and exact destination residence. Add negatives before copy, before bind, and before activation; the happy and post-COMMIT retry paths must remain green. If the cross-instance validation reveals an unavoidable ceremony limitation, stop and document it rather than weakening the sequence silently.

## P2 hardening carried from the copy review

The DB publisher now rejects a FIFO safely, but the config path still uses blocking `O_RDONLY` in `_read_config_at()` and `_publish_bytes_at()` before checking that it is regular. A FIFO substituted at the destination config basename can block stage discovery or publication indefinitely. Use nonblocking/no-follow opens plus `S_ISREG` for existing config artifacts as well; make `_write_all()` fail on a zero-byte write. A small FIFO/zero-write pin is sufficient.

Keep wait/CLI paused. After the source route is explicit and decommission is activation-gated, rerun the complete move matrix and return one frozen revision.
