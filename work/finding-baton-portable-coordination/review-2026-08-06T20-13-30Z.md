The corrected handoff hashes and counts match, and the immutable `moves` authority plus no-follow identity helper closes the symlink repro. Static review found one unhandled input that breaks move semantics and several places where the new authority is not yet consumed completely.

## P1 — source and destination may be the same instance directory

`maintenance_enter(move=True)` captures both directory identities but never requires them to differ. A destination config with another basename in the source directory is accepted. Because `mailbox.sqlite3` has a fixed name, copy/bind/activate operate on the source DB itself. Activation then leaves both the old source config and new destination config as writable aliases to the same active authority; there is no source left to decommission and the claimed location move did not happen.

Independent result against the frozen pair:

`same_dir_entered <token>`

`copy ... stage='copied'`

`bind {'bound': True}`

`activate {'activated': True}`

`same_db_two_config_routes_writable ['source_config', 'destination_config']`

Reject a move at `maintenance_enter` when source and destination directory identities are equal, regardless of config basename. Pin both the exact same config path and a different config basename in the same directory. The source must remain active and unchanged after each refusal.

## P1 — some move decisions still bypass the immutable binding

The new `moves` row is described as the single authority, but several checks still trust duplicated live/path data or omit its identity checks:

1. `move_copy()` derives `dest_config` from `instance_meta.move_peer`, not `binding.destination_config`, and its existing-destination stage-discovery returns `copied`/`bound`/`activated` without validating the destination Store against the bound destination `{path, dev, ino}`. A replaced destination directory can therefore be reported as a valid completed stage even though bind/activate would later reject it.
2. `move_decommission()` full-opens the destination and validates UUID/status/ceremony, but does not call the binding's destination identity check. It should not decommission the source against an active clone placed at a replaced destination route.
3. `_move_binding()` does not verify `moves.instance_uuid` against the open Store's immutable instance UUID. Every consumer assumes that relation.
4. `_validate_route_identity()` verifies that the committed route is canonical and that parent identity/basename match, but never requires the caller's actual `self.config_path` to equal that exact committed canonical path. Its documentation and handoff claim that it does.

Make the binding row the only route/identity source: validate `{token, instance_uuid}` once, derive source/destination paths from it, require exact canonical Store config path plus held/opened parent identity, and invoke that validation before every stage return and before source decommission accepts the destination. If the duplicated `move_peer`/`move_source` live fields remain for quick status/shape, explicitly cross-check them against `moves` rather than using them as authorities.

Add pins for:

- destination directory replacement before `move_copy()` stage discovery (all copied/bound/activated stages fail closed);
- destination replacement before decommission;
- binding UUID mismatch as corruption;
- noncanonical or alternate caller spelling of a bound config path refusing rather than being normalized silently.

The current helper is private, but the schema's stated fail-closed contract should encode the lifecycle it claims.
