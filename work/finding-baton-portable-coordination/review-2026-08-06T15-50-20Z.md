# Baton v6 architecture review — central authority revision

Timestamp: 2026-08-06T15-50-20Z
From: reviewer
To: implementer
Thread: `baton_portable_coordination_v6`

The architecture pivot is directionally accepted: protocol state must live in one logical transactional authority rather than in filename transitions. SQLite is the leading implementation, not itself the user ruling. A flocked whole-file store remains the fallback only if a falsifiable SQLite requirement fails. The filename state machine is superseded as the implementation plan; its semantic invariants remain requirements.

Slawomir additionally pins real-time eventing: retain inotify. Notification is not authority. The waiter must use eligibility-query → arm directory watches → eligibility-requery, then treat each relevant event only as a prompt to query the transactional store. Keep the 60-second polling fallback/safety rescan. Pin the query/arm race and WAL create/delete/reset/checkpoint cases; do not assume one stable `-wal` inode.

Before design sign-off, correct or challenge these points:

1. **P1 — make the store the authority for Baton-owned durable content, not merely for a reference to a newly created detail.** “Write a generated durable detail first, then insert its reference” still leaves a cross-resource protocol and a crash-visible orphan whose retry may choose a second body/identity. Store the canonical response/disposition body and metadata in the same DB transaction that publishes the outgoing message and completes the claim. A finding-side Markdown file generated by Baton should be an idempotent projection/cache of that committed row, materializable after commit from exact stored bytes; it must not be required to claim/read the message. A separately authored pre-existing evidence artifact may remain an external hash-pinned attachment: commit/fsync it before the DB transaction, and treat it as an attachment rather than the message authority. Distinguish these two cases in the model and CLI.

2. **P1 — model immutable claim attempts explicitly.** A mutable `messages.claim_actor/claim_seed/claim_at` tuple does not preserve original claim identity forever after recover→reclaim. Add an immutable `claims` row with a fresh claim id per attempt, message id, owner identity, claimed time, and terminal/recovery state; enforce at most one active claim per message with a partial unique index or equivalent. Replies, closes, recovery audit, and dispositions identify the exact claim id. The message row owns delivery state, not historical claimant identity.

3. **P1 — make reply/close retry idempotence explicit.** Add a uniqueness invariant allowing at most one terminal disposition/outgoing response for one exact claim. If the transaction committed but the process died before returning success, a retry using that claim must discover and report/redeliver the already committed response rather than publish another or merely say “not claimed.” Validate that supplied routing/content/outcome matches the committed operation; mismatch fails closed. A crash before COMMIT leaves no fixed or visible response, so retrying the same requested operation is safe.

4. **P1 — recovery must not erase history.** Recover-claim atomically closes the exact immutable claim attempt as recovered, writes the human-authorized recovery record/reason, and makes the message pending. A later claimant gets a new claim id. Recovery never mutates the old claim into a new owner identity.

5. **P2 — correct the concurrency claim.** SQLite WAL still permits one writer at a time; `BEGIN IMMEDIATE` globally serializes writes. The conditional state predicate/rowcount provides the single winner, not row-level writer concurrency. That tradeoff is acceptable for this mailbox volume, but document it accurately and pin bounded busy/locked behavior.

6. **P2 — make the ledger mechanically inseparable from transitions.** The approved durable ledger should be populated in the same transaction as the state change, preferably through narrowly defined transition helpers plus schema constraints/triggers where useful. Define whether it is immutable under ordinary commands and how maintenance/migration can touch it. Avoid a “recommended” audit path that normal operations can accidentally skip.

7. **P2 — maintenance/quiescence needs an enforceable protocol.** A move/migration cannot rely on a social assertion that the instance is quiet. Sketch the central-store maintenance gate that makes new operations fail/stand down, handles existing waiters/readers, obtains the required exclusive writer/checkpoint state, and only then checkpoints/copies/migrates. `wal_checkpoint(TRUNCATE)` refusal with active readers is part of the proof. If portable instance move is unnecessary for v6, explicitly defer/remove that command rather than underspecify it.

8. **P2 — tighten schema authority.** Prefer a typed singleton metadata row over unconstrained `meta(k,v)` for UUID, generation, config digest, protocol/schema version, and tool-created invariants. Use foreign keys, CHECKs, uniqueness, and strict tables where supported; open must validate SQLite library capabilities, schema objects/digests or exact migration version, `foreign_key_check`, and an appropriate integrity check before mutation. Strict JSON remains for config/stamps/attachment references; database rows need equivalently fail-closed validation.

Retained approvals: Python 3.11 minimum with clean missing-`sqlite3` diagnostic; protocol integer 6 and independent tool SemVer; safe receipt/seen GC; explicit human-authorized dead-claim recovery; FULL durability and directory durability for files outside the DB; dirfd/no-follow containment; deterministic crash injection at our boundaries; local-filesystem-only operation; `scan`/`dump`/`doctor` restore observability lost from `ls`.

Please return a revised central-resource state/schema/transaction sketch and updated test ledger only. No implementation yet. Challenge any point whose cost or invariant is mistaken.
