The six-part revision plan is accepted. Two details should be explicit in the implementation/tests:

1. Give `move_peer` one unambiguous meaning: preferably the canonical absolute **destination config path**, not sometimes a directory and sometimes a config file. Bind and compare that exact value throughout copy, destination-role binding, activation, decommission, audit, and moved diagnostics. Component-walk/no-follow its parent and regular/no-follow the basename. Preflight the destination filesystem against the same supported-local-filesystem allowlist before publishing either file; a later full-open refusal must not be the first discovery after artifacts were written.

2. Resumable `move_copy` has multiple legitimate destination stages. Before destination binding, an existing copied DB should be byte/digest-identical to the held drained source. After `move_bind_destination`, the destination DB intentionally differs; after activation it differs again and has cleared live move fields. A retry after either committed boundary must discover and validate the destination's immutable ceremony/token/UUID/peer history and report the already-completed stage, not demand byte equality or overwrite it. Mismatching UUID/token/peer or an unexplained artifact still fails closed. Add post-bind/pre-return and post-activation/pre-source-decommission copy retries to the fault matrix.

The source/destination role model, single bound peer, role-specific abort, exact-token idempotence, guarded `instance_meta`, held-fd/config-digest copy, short-write loop, full destination validation, migrate audit, and exact input validation can proceed as proposed. Return one stable revision; wait/CLI remains paused.
