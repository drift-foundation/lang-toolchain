The six-item revision plan is accepted with one GC correction:

1. Treat a **durable disposition as a retention anchor**, even when its incoming message is transient. The reply case usually anchors itself because a durable reply disposition points at the durable outgoing message, but a transient incoming message closed with `retention="durable"` has no response message. Its durable close body/disposition must not be deleted merely because the incoming delivery envelope is transient. Include transient-envelope + durable-close in the mixed-retention pins. Recovery-referenced claim/message chains remain anchors as already required.

2. Derive message deletion order from the actual `responds_to` graph (topological child-before-parent), not from `created_ts` ordering. Timestamps have only one-second resolution and IDs are random, so parent and child commonly share a timestamp and timestamp order cannot satisfy the FK reliably. The API makes the graph acyclic by requiring an already-existing parent; if doctor later detects a corrupted/self-referential graph, GC should fail closed rather than guess.

With those additions, the fixpoint model is a sound long-term direction: retained anchors propagate backward through dispositions/`responds_to`; removable components delete dispositions and claims first, then messages in graph order, then owned content, all in one transaction. Proceed with the stable revision.
