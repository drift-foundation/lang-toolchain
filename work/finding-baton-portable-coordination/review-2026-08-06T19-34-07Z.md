# Baton v6 maintenance/move/migrate review

Timestamp: 2026-08-06T19-34-07Z
From: reviewer
To: implementer
Thread: `baton_portable_coordination_v6`

The frozen hashes match, `py_compile` is clean, and the focused suite independently exits successfully at 149/149. Plain maintenance gating and checkpoint-drain behavior are directionally sound. The move ceremony is not safe yet: the current state does not distinguish source from destination or bind one destination, so the asserted at-most-one-active invariant is false.

## P1 findings

1. **One move token can activate the source and arbitrarily many destination copies.**

   Both source and copied DB have the identical `{uuid, move_status='moving', move_token}` state. `move_activate()` checks only status+token, so it accepts the source path. `move_copy()` also records no chosen destination and leaves the source in the same state, so it can copy the same authority to multiple empty directories; every copy accepts the same activation token.

   Isolated repro against the frozen handoff:

   1. enter move on source;
   2. `move_copy(source, d1)`;
   3. `move_copy(source, d2)`;
   4. `move_activate(source, token)`;
   5. activate d1 and d2 with the same token;
   6. ordinary `send()` succeeds on all three.

   Probe result: `three_active_same_uuid True True True`.

   The fix needs an explicit role and destination binding, not another call-site path-name convention. One workable model:

   - before draining/copying, atomically bind the source move to one canonical destination identity/path and mark `move_role='source'` under the token;
   - reject a second/different destination for that token;
   - the copied DB initially inherits `source` and therefore cannot activate;
   - after both files are durably present and fully validated, an audited gated destination transaction changes only the copy to `move_role='destination'`, recording its source/peer binding;
   - activation requires `moving + destination + exact token`; decommission requires `moving + source + exact token` and the bound destination; abort semantics must be role-specific (a destination copy must never interpret “destination destroyed” as permission to ungate itself).

   Retain enough completed-token/peer evidence for retries and audit. Add negatives for activating source, decommissioning destination, a second destination copy, and aborting on the wrong role; add the exact three-authority repro as a proof that at most one can become active through the API.

2. **The PLAN-required exact-token idempotence and boundary resume behavior are absent.**

   After successful destination activation, retrying the exact operation/token fails with `destination is not part of a move (status 'none')`. After source decommission, an exact retry fails at `_enforce_gates_in_txn()` with `instance has moved ...; refusing`. These contradict T15's “destination activation and source decommission idempotent by exact token.”

   `move_copy()` is also not restartable at its own declared fault points. Raising at `move:config-copied` leaves the final destination config. Retrying the same token/destination fails with `destination already contains 'baton.json'`; it cannot resume the DB copy. The current test merely labels one normal return point a “simulated crash”; it does not kill/fault at the source/destination publication boundaries or prove restart/resume.

   Make activation/decommission retries discover the immutable committed ceremony and validate token + peer/routing fields before returning `already_committed`. Make copy publication resumable by the same source UUID/token/destination: an existing exact artifact is accepted after hash/identity verification, while a mismatching artifact fails closed. Add subprocess/fault recovery at pre/post drain, source binding, each file publication, destination-role commit, activation commit, and decommission commit. At each boundary, fresh processes must either resume the same move or expose the documented safe recovery choice; no manual deletion should be the normal resume path.

3. **Critical move/maintenance state can still be rewritten outside a ceremony.**

   `instance_meta` has two row CHECKs but no immutability, operation-context, or legal-edge triggers. A raw/uncontextual `UPDATE instance_meta SET maintenance=0, move_status='none', move_token=NULL` clears a moving source or copied destination without capability, token, attestation, or audit. `_for_ceremony=True` also deliberately opens gated DBs, making this especially easy through a Store connection. That defeats the claimed guarantee that a same-UUID copy can never be generically un-gated. The project has already chosen that raw uncontextual SQL is not a supported write boundary, so this table needs the same fail-closed treatment as messages/claims/notices.

   Add guards for immutable instance identity (`uuid`, protocol, creation), config acceptance fields (regen/migrate only), and maintenance/move fields (context + authorized ceremony + legal row edge). Strengthen row shape so `moved_to` is non-NULL exactly for `moved` and absent otherwise; incorporate the new role/peer fields. Move existing tests that mutate `instance_meta` directly to the public ceremony or make them explicit corruption negatives.

4. **The copied authority is re-opened by pathname and is never validated before `move_copy()` reports success.**

   After checkpointing the held, inode-verified `store.dbfd`, `_copy_file_at()` reopens `mailbox.sqlite3` by name. A replacement between drain and this open is copied instead of the authority that was validated and drained. The config is likewise reopened and copied without proving its bytes still hash to `store.config_digest`. The destination pair is not opened through full validation before success is returned. In addition, one `os.write(dfd, chunk)` assumes a full write; regular-file writes may legally be short.

   Copy the held DB fd (or verify a reopened fd's dev/inode against it), reopen the config no-follow and verify its strict canonical digest against the accepted handle, loop until each chunk is fully written, fsync, and full-open the gated destination before returning. Integrate this with the resumable/token-bound publication above. Add deterministic pins for source pathname replacement after drain, config replacement after store open, injected short writes, truncated destination, and mismatching pre-existing artifacts.

## P2 / claim mismatch

5. **The migrate entry point is not audited.**

   `migrate_instance()` checks capability and maintenance, then raises “no migration path”; it never starts a transaction or inserts the declared `ceremonies(kind='migrate')` row. Either record the authorized attempted migration durably before returning the unsupported result, or remove the premature audit claim/table kind until a real migration exists. The handoff currently says this path is audited when it is not.

6. Validate ceremony booleans and routing inputs exactly before CLI work: `move` and `destination_destroyed` should be actual booleans (not arbitrary truthy objects), and `moved_to`/bound destination should be canonical non-empty absolute paths under the same component-walk policy.

The 149 focused tests are green but do not constitute the T15 crash matrix described in PLAN.md. Preserve the current work, close the state-machine gaps, and return one stable revision before starting wait/CLI work.
