# Baton v6 central-store review — transaction sequencing and lifecycle

Timestamp: 2026-08-06T15-53-52Z
From: reviewer
To: implementer
Thread: `baton_portable_coordination_v6`

Round 12 closes the prior eight items and confirms the central-authority architecture. The state/resource choice is now clear enough; these remaining gaps concern correctness of the concrete SQLite plan, not a return to filename state.

1. **P1 — the maintenance checkpoint sequence is invalid as written.** I reproduced the exact shape against stdlib SQLite in WAL mode: after `BEGIN EXCLUSIVE`, `PRAGMA wal_checkpoint(TRUNCATE)` raises `OperationalError: database table is locked` on the same connection. In WAL mode `BEGIN EXCLUSIVE` also does not exclude readers the way the wording implies. Revise the ceremony: commit the maintenance flag first (after it serializes behind prior writers); all cooperative operations then refuse new work, waiters/readers drain; execute `wal_checkpoint(TRUNCATE)` with no active transaction and require its busy count to be zero; verify WAL/SHM state; then copy/migrate while maintenance remains set. Spell out maintainer ownership and destination/source flag/generation handling for move. Do not use an open SQLite transaction as the cross-filesystem copy lock.

2. **P1 — retention lifecycle is missing from the DB model.** If completed transient messages/dispositions retain their bodies, v6 silently changes the v5 transient contract and the database grows with supposedly ephemeral content. Define the exact transaction that scrubs/deletes transient canonical bodies after consumption while retaining only the minimum idempotence/audit metadata (at least content hash, routing, outcome, exact claim/disposition identity). Durable bodies remain materializable. A post-commit retry of a transient response may report the already-committed identity/hash after its outgoing message was consumed; it cannot promise to re-materialize bytes that the retention contract deliberately erased. Define bounded GC for completed metadata and the append-only ledger, or explicitly state which audit metadata is retained permanently and why.

3. **P2 — avoid two canonical copies of a reply body.** The sketch places the same body in both the outgoing `messages` row and `dispositions`. Prefer one canonical content owner: for a reply, the disposition references the outgoing message/content row; for a close, the disposition owns/references content directly. A normalized immutable `contents` row is another valid answer. Whatever shape is chosen, constraints and retry comparison must not permit the disposition hash/body to drift from the outgoing message.

4. **P2 — make ledger attribution mechanically defined.** Triggers can guarantee that a transition row exists, but the proposed transition includes actor/seed and a trigger has no implicit knowledge of the current Baton actor. Specify the transaction-scoped operation context (for example, a constrained singleton context row set by each writer in the same serialized transaction, or registered connection functions that make uncontextual mutation fail closed). The direct-SQL trigger test must not silently emit unattributed or stale attribution. Include old/new state graph validation, not just logging.

5. **P2 — complete event and deployment edges.** The inotify waiter must treat queue overflow, watch invalidation, directory replacement/unmount, and WAL/SHM create/delete/reset as requery-and-rearm or clean degraded polling conditions; events remain hints only. State the required SQLite library floor explicitly (`STRICT` requires SQLite 3.37.0) rather than saying both “where supported” and “fail if absent.” Finally, update the cutover proof for this pivot: drain/close every v5 claim/pending/notice and stop every v5 waiter before creating protocol 6 state; no dual reader/importer is retained unless Slawomir separately approves it.

Please revise the design/test ledger only. No implementation yet. If the maintenance command can be simplified or removed while still meeting the already locked instance-move goal, challenge that rather than adding an unsafe pseudo-lock.
