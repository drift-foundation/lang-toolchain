Round 13 correctly closes the checkpoint, retention, content-shape, attribution, event, and one-way-cutover questions. Two remaining P1s follow directly from the newly locked “one logical authority” invariant.

1. **P1 — mutable instance identity/config acceptance is still mirrored across SQLite and `instance.json`.** The sketch keeps UUID, protocol, generation, and config digest in `instance_meta`, cross-checks them against `instance.json`, and copies both. That creates an impossible atomicity requirement for `regen`: accepting a new strict-JSON config would have to update both SQLite and `instance.json`, with a crash window that can strand disagreement. Collapse mutable accepted instance metadata into SQLite. `baton.json` remains the explicit external policy input; one DB transaction accepts its exact canonical digest/generation after validation. The DB owns UUID, protocol/schema, accepted config generation/digest, maintenance, and move status. Prefer deleting `instance.json`; if a small bootstrap/locator file is truly necessary, make it immutable/non-authoritative and prove that no normal transition ever needs to update it. Refresh init, regen, open, doctor, move, and cutover tests around that rule.

   The source-side move tombstone has the same issue if it is implemented by replacing an authoritative `instance.json`. Express source decommissioning in the source DB while its maintenance gate remains set, or justify a non-authoritative external marker. A cross-filesystem move cannot atomically activate destination and decommission source, so document the recoverable order and prove that every crash point leaves at most one instance eligible for ordinary operations. The copied source DB starts gated; destination activation and source decommission tokens must make an accidental human stale-flag clear fail closed rather than fork one mailbox UUID into two active authorities.

2. **P1 — `contents.sha256 UNIQUE` conflicts with transient scrubbing.** Global hash uniqueness deduplicates identical bytes across messages. If one transient message and one pending/durable message share a contents row, consuming the transient message cannot delete that row without either violating the foreign key or erasing still-live content. This is unnecessary deduplication. Give each logical message/close content its own immutable `content_id`; index SHA-256 if useful but do not make it globally unique. Transient scrub deletes only that content row after clearing its sole owning reference in the same transaction. If you prefer deduplication, supply a correct reference/retention-count model and its race tests, but the simpler per-owner row is recommended. Clarify that “immutable” forbids body mutation, not the authorized consuming-transaction deletion required by transient retention.

Also pin the CLI invariant inherited from the earlier v6 design: generated body and separately authored attachment are either explicitly XOR, or Slawomir must approve expanding the surface to body-plus-attachment. Do not let the schema pivot silently change that contract.

Return the revised design/test delta only; no implementation yet. Once these are resolved, consolidate the finding into one current implementation plan instead of requiring the implementer to reconstruct it from thirteen rounds.
